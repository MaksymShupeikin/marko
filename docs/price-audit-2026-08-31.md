# Аудит сопоставления и извлечения цен — 31 августа 2026

## Вердикт

Текущий результат проекта действительно сильный: оба пойманных заказчиком денежных бага
закрыты, в трёх сохранённых отчётах нет общего фолбэка статистики, а якоря рекомендаций
выглядят предметно правдоподобными. Но движок пока нельзя считать fail-closed для точной
денежной рекомендации. Аудит подтвердил пять классов механизмов, которые при определённом
сочетании тонкого рынка, ошибочного идентификатора или нестабильного LLM-вердикта способны
дать неправильный якорь.

Это не означает, что текущие рекомендации массово неверны. Доступный Redis содержал только
3 отчёта `v11` и 98 уже прошедших гейты предложений. Поэтому числа ниже — нижние границы и
примеры механизмов, а не оценка распространённости по всему каталогу.

Ни один продуктовый фикс в ходе аудита не реализован.

## Топ-5 по потенциальному денежному ущербу

### 1. C2 — фолбэк статистики возвращает пониженные предложения в расчёт

`_stats_prices` сначала исключает предложения с `confidence < 0.7`, но если сильных осталось
меньше трёх при общем количестве не меньше трёх, возвращает **все** цены. Офлайн-пробник на
текущем коде: 2 сильные цены `500/520` и 3 пониженные `50/100/120` дают минимум `50` и
рекомендацию `47`. То есть второй проход или фото-гейт может понизить подозрительную цену до
`0.5`, после чего статистический фолбэк снова сделает её якорем. В сохранённых данных общий
фолбэк не сработал ни в одном из 3 отчётов, но сработал в 1 из 12 блоков источников: Google
с двумя сильными предложениями и пониженной Rozetka-ценой `365` показал source-min `365`.
На общий отчёт это не повлияло, потому что в нём было 33 сильных цены.

Предлагаемый фикс: разделить «видимые предложения» и «цены, имеющие право формировать точную
рекомендацию». Если после всех проверок сильных цен меньше трёх — `recommended_price = null`,
а широкую выборку показывать отдельно с явным статусом «недостаточно подтверждённых данных».
Не лечить это дополнительными LLM-вызовами: детерминированный контракт дешевле и надёжнее.

### 2. B1 — модель автомобиля хранится как OEM и даёт чужому товару score `0.9`

В реальной базе четыре разных листинга содержат `PEUGEOT206` в `oem_numbers`; у листинга
прокладки коллектора первыми термами идут `PEUGEOT206`, `PEUGEOT207`. Текущий matcher считает
такое значение самодостаточным номером: совпадение подстроки даёт `0.9` без проверки темы.
Живой Serper-запрос `PEUGEOT206` вернул 7 результатов; текущий `_candidates` принял с `0.9`
три страницы о продаже или характеристиках **целого Peugeot 206**, а не прокладки.

Один принятый кандидат `reono.ua/peugeot/206` ответил HTTP 200; текущий
`_structured_price` извлёк из его raw HTML `600 USD` и изображение автомобиля. В одиночном
тонком отчёте такая цена проходит `_drop_implausible`, потому что outlier-гейт включается
только от четырёх предложений. Контраргумент проверен: изолированный первый LLM-проход трижды
дал для этого конкретного priced-кандидата `no`. Однако другая принятая страница автомобиля
на трёх одинаковых повторах получила `analog → same → no`; её цена не проверялась. Поэтому
единый end-to-end ложный денежный оффер в одной фикстуре не доказан, но LLM не является
детерминированной защитой от дефекта идентификатора.

Предлагаемый фикс: применять строгий `part_number()` ко **всем** путям формирования OEM,
отделить модель/машину от каталожного номера, не добавлять сырой SKU через `normalize_oem`,
а для модель-подобных токенов (`PEUGEOT206`) требовать тематическое совпадение даже при
длине больше 8. Живой запрос по такому токену не должен доходить до page-fetch.

### 3. B8 — тонкий рынок отключает обе дорогие проверки, но рекомендация остаётся

`_indexed_anchor` возвращает `None`, когда сильных цен меньше трёх. После этого и
`_verify_offers`, и `_photo_check_offers` завершаются без проверки. При этом `_stats_prices`
для одной-двух сильных цен всё равно формирует минимум и `_recommended_price`. Получается
обратная зависимость: чем слабее доказательная база, тем меньше защит проходит якорь.
В трёх доступных кешированных отчётах тонких общих рынков не было (`0/3`), поэтому частота
не установлена.

Предлагаемый фикс: для `<3` сильных цен точную рекомендацию не выдавать; семантический гейт
и проверку фото самых дешёвых кандидатов выполнять без медианы, используя абсолютные
правила. Это одновременно закрывает B8 и не требует массового увеличения LLM-бюджета.

### 4. A2/A3/A5 — цена извлекается без достаточного контекста происхождения

Текущий парсер: считает отсутствующую JSON-LD валюту гривной; в microdata игнорирует рядом
стоящий `priceCurrency=USD`; рекурсивно берёт первый `Offer` из любого JSON-LD-узла; в
сниппете берёт первое распознанное число. Живая фикстура Rozetka от 31 августа подтверждает,
что исправленный формат `от 365 ₴ x 6 ; от 365 ₴` теперь даёт `None`. Другая живая выдача
содержит категорийный сниппет `9 750₴. 6 450₴`; текущий парсер возвращает старую цену
`9750`. На страницах условий рассрочки он извлекает `1`, `500`, `3000` или `20000 грн` как
цену. Для этих информационных страниц доказан формат, но не прохождение matcher конкретного
товара.

Предлагаемый фикс: извлекать цену только из главного `Product`/канонического товара,
связывать `Offer`, валюту и изображение с одним узлом; без валюты не угадывать UAH;
детерминированно распознавать «від», доставку, кредитные/минимальные суммы и порядок
old-price → sale-price. Не-product URL отсеивать до скачивания страницы.

### 5. C1 — первый LLM-проход изменяет состав рынка на идентичном входе

Минимальный замороженный реплей: 25 самых дешёвых Prom-предложений одного сохранённого
отчёта, 3 одинаковых запуска, всего 3 вызова `gpt-5-nano`. Первые два прогона совпали
(`24 same, 1 analog`), третий дал `21 same, 4 no`. Дрейф — 4/25 (`16%`); среди изменившихся
был товар с точным номером `312 937`: `same → same → no`. Отдельный B1-batch подтвердил
ещё более резкий дрейф `analog → same → no` для страницы целого автомобиля.

Предлагаемый фикс: перенести право включения в денежную статистику в детерминированные
правила; LLM использовать как дополнительный сигнал. Кешировать вердикт по нормализованному
контексту запроса и кандидата. Majority vote не рекомендуется как основной фикс: он втрое
увеличивает стоимость и лишь снижает, но не устраняет недетерминизм.

## Масштаб и происхождение доказательств

Точка отсчёта:

- ветка `marko-core`, `HEAD=da948a9d68d3967e74522ceeec1f8ca69058cc3d`;
- до аудита рабочее дерево было чистым;
- `origin/marko-core=b9c301e`, локальный `da948a9` — handoff-коммит без изменения движка;
- PostgreSQL/Redis принадлежат общему Docker-проекту `marko`; сами контейнеры данных были
  первоначально созданы compose-контекстом соседнего checkout. Это dev/shared-data
  свидетельство, а не production-снимок.

Использовано:

- PostgreSQL: 4 901 листинг, 12 133 элемента `raw_data.oem_numbers`;
- Redis `competitor-prices:v11:*`: 3 отчёта, 98 сериализованных предложений;
- Redis `photo-used:v1:*`: 11 вердиктов (`5 used`, `6 not_used`), из них 7 сопоставлены
  с предложениями сохранённых отчётов;
- живой Serper: 3 запроса;
- живой LLM: 6 вызовов `gpt-5-nano`;
- независимые HTTP page-fetch: 2 (`403` anti-bot и `200` raw page);
- Prom/avto.pro fetch: 0;
- полные живые отчёты: 0;
- Redis/DB writes и `refresh=True`: 0.

Экономия относительно максимального бюджета: Serper `3/30`, LLM `6/60`, Prom/avto.pro
`0/100`. Полные отчёты не запускались: они одновременно тратили бы десятки вызовов,
перемешивали дрейф SERP/рынка/модели и рисковали перезаписать видимый заказчику кеш.

## Фото-проверка: что доказано и что нет

Снимок photo-cache содержит 11 вердиктов: 5 `used`, 6 `not_used`. С семью предложениями
удалось сопоставить URL. В отчёте `06E145100R` предложение Prom за `2500` имеет cached
`used`, состояние `used`, confidence `0.5` — оно видимо, но вне общей статистики.

Эти числа **не являются accuracy-метрикой**. Без человеческой ground truth нельзя считать
`used` правильным, а `not_used` — успешной проверкой. Информативны только размеченные false
negative на Б/У-фото и false positive на новой детали. Такой датасет в ходе экономного
аудита не создавался.

## Acceptance-контракт для будущих фиксов

Фикс нельзя принимать только по новым синтетическим тестам. Минимальный набор:

1. Все raw-файлы этого аудита проигрываются офлайн без внешних вызовов.
2. Реальный `PEUGEOT206` Serper payload даёт 0 чужих car-page кандидатов **до page-fetch**.
3. Raw `reono.ua` не может связать `600 USD` с листингом прокладки независимо от LLM.
4. `2 strong + 3 demoted` не возвращает weak minimum; recommendation = null.
5. Рынок из 1–2 сильных цен не получает точной рекомендации без дополнительных доказательств.
6. Реальный Rozetka installment остаётся no-price; `9750/6450` либо даёт sale `6450`, либо
   fail-closed, но не `9750` как первое число без контекста.
7. Одинаковый frozen input не меняет deterministic eligibility при любом LLM verdict.
8. После focused regression — полный backend suite и один **отдельно разрешённый** живой
   отчёт с сохранением сырья и без перезаписи пользовательского кеша.

## Воспроизведение

Все команды выполняются из корня репозитория.

```bash
backend/.venv/bin/python scripts/price_audit/static_probes.py
backend/.venv/bin/python scripts/price_audit/mine_cached_reports.py
backend/.venv/bin/python scripts/price_audit/analyse_serper_fixtures.py
backend/.venv/bin/python scripts/price_audit/analyse_page_fixtures.py
docker exec -i marko-db-1 psql -U marko -d marko -f - < scripts/price_audit/catalog_probes.sql
```

LLM/Serper/page capture scripts имеют собственные hard caps. Их повторный запуск снова
тратит бюджет и не нужен для проверки уже сохранённых результатов.
