## Сделано: пункт B — потолок и порядок семантической проверки

`CH-0015` в `.artifacts/improve-20260730/CHANGES.jsonl`, валидатор §11.3 даёт
`ОШИБОК: 0` на всех 15 записях.

Было: `_ensure_observation_ids` обходил наблюдения по `MarketObservation.id`,
без сортировки по цене и без потолка, одним `asyncio.gather` на всю когорту.

Стало:

- обход **снизу вверх по цене** (`price ASC`, `id` только для разрыва ничьих,
  чтобы порядок был воспроизводим);
- **ранняя остановка** после `pricing_llm_max_confirmed_reviews` подтверждений;
- потолок **на позицию, а не на цель сбора**. `ensure_target_comparability_reviews`
  теперь группирует наблюдения по `pricing_run_item_id`; без этого одна дешёвая
  позиция съедала бы бюджет соседней. Группы идут параллельно через один
  семафор, так что провайдер по-прежнему видит не более
  `pricing_llm_max_concurrency` вызовов одновременно.

Пара чисел: когорта из 30 сопоставимых предложений — **30 вызовов → 12**.
Остановка проверяется между волнами, поэтому перелёт ограничен одной волной
(`ceiling + max_concurrency`), а не отменяет уже начатую работу.

**Значение по умолчанию 10 выбрано равным `pricing_scraper_max_sellers=10`** —
это тот же потолок, который уже применяет сборщик, поэтому на сегодняшних данных
поведение не меняется. Это не назначение доменной величины: величина не новая,
она равна действующей.

Мутационная проверка §3.2, три мутации собственного фикса:

| Мутация | Результат |
|---|---|
| `confirmed >= ceiling` → `>` | убита (`test_ceiling_stops_exactly_on_the_boundary`) |
| удалить `break` | убита (два теста) |
| считать вызовы вместо подтверждений | **сначала выжила**, тест усилен, затем убита |

Третий мутант выжил на первом заходе: тест «когда ничего не подтверждено»
использовал 12 наблюдений, что при волне 4 исчерпывается за 3 волны и не даёт
остановке сработать. Поднял до 30. После правки мутант убит.
Дерево после проверок восстановлено побайтово (`diff -q` — identical).
