# Спецификация парсеров

Три независимых канала данных. У каждого — вход, выход, правила и критерии
приёмки. Если поведение кода расходится с этим файлом — баг в коде.

Код: `backend/src/marko/parsers/{prom,prom_export,avtopro}`,
оркестрация — `services/catalog_import.py`, `services/matching.py`.

---

## 1. Импорт магазина по ссылке (prom.ua)

**Вход:** публичная ссылка на магазин prom.ua.
**Выход:** строки `listings`, ключ — `(marketplace, external_id)`.

Поток: `POST /api/v1/stores` создаёт `sync_run`, ставит Celery-задачу и
возвращает `202`. Worker обходит публичные страницы каталога (постранично,
с расширением товарных групп), парсит Apollo-кеш страницы и пишет товары
пачками. Клиент опрашивает `GET /api/v1/jobs/{id}`.

**Правила:**

- повторный импорт того же магазина **обновляет** товары, а не дублирует;
- пропуск страницы не роняет весь импорт (нестрогий режим), но каждая
  пропущенная страница должна попасть в счётчик ошибок задачи;
- вежливость к источнику: пауза `delay` + джиттер между запросами, ретраи
  только на 429/5xx, до `max_retries`;
- `sync_run` обязан завершиться в одном из терминальных состояний, даже если
  упал worker — «вечный running» это баг.

**Приёмка:**

- [ ] на магазине ≥ 1000 товаров импорт доходит до конца и число товаров
      совпадает с числом на витрине ±1%;
- [ ] в `sync_run` видно: обработано страниц, создано, обновлено, ошибок;
- [ ] повторный запуск не меняет `total`, а только `updated_at`;
- [ ] у пользователя в UI число «импортировано N» совпадает с базой.

> ❓ Решить: что делать при частичном импорте (30% страниц упали) — считать
> задачу успешной с предупреждением или провалившейся.

## 2. Импорт XLSX-выгрузки Prom

**Вход:** файл из кабинета продавца (`Export Products Sheet`, иначе первый
лист). **Выход:** те же `listings`; магазин определяется по хосту товарных
ссылок (`kemp-cs2847093.prom.ua` → продавец `2847093`), поэтому файл и ссылка
наполняют один и тот же магазин.

Колонки ищутся по названию заголовка, порядок не важен (таблица соответствий
— в `docs/sources.md`).

**Правила по OEM-номерам** (от них зависит вся проверка цен):

- собираются `Код_товару`, `Номер_пристрою_(MPN)`, характеристики
  «Код запчастини» и «Кросс-номери»;
- нормализация: верхний регистр, без пробелов и разделителей;
- дедупликация с сохранением порядка, слишком короткие отбрасываются;
- результат — `listings.raw_data->'oem_numbers'`, **первый номер считается
  основным** и именно он идёт в avto.pro.

**Приёмка:**

- [ ] строки без пригодной ссылки/цены пропускаются, но **попадают в отчёт**
      с причиной (сейчас причина не показывается — см. `known-gaps.md`);
- [ ] на реальной выгрузке (эталон — 4901 товар) OEM определён у 100% строк;
- [ ] повторная загрузка того же файла даёт 0 созданных и N обновлённых.

## 3. Цены конкурентов на avto.pro

Самый хрупкий канал: это скрейпинг чужого сайта за антибот-защитой.

**Вход:** OEM-номер + (опционально) бренд + (опционально) название товара.
**Выход:** список предложений с ценой, продавцом, городом и наличием.

Поток (`parsers/avtopro/gateway.py`):

1. `PUT https://avto.pro/api/v1/search/query` с `{"Query": oem}` →
   список **suggestions** (интерпретаций номера: один номер часто висит на
   нескольких марках);
2. выбор нужной suggestion (см. правила ниже);
3. GET страницы детали → таблица предложений;
4. дозагрузка через continuation-токен кнопки «Показать ещё», не более
   `max_search_pages` страниц (в API сейчас 2).

**Правила выбора марки — критичны, здесь чаще всего «мусорный» результат:**

1. если передан `brand` — берём suggestion, у которой совпал бренд или
   `brand_path`;
2. иначе, если передан `name` — берём ту, чьи слова (без цифр) пересекаются с
   названием товара; сравнение идёт и по `title`, потому что сборные марки
   («VAG/VW/Skoda/Seat/Audi») лежат только там;
3. иначе — top-1 из выдачи.

**Top-1 регулярно оказывается чужой маркой** («China», «BENTLEY»), поэтому
шаг 2 обязателен в реальном сценарии. Любой вызов из UI, который не передаёт
`name`, эксплуатирует худший из трёх путей — это ровно то, что делает
результат «нормальным у Клода и мусорным у человека».

**Правила по данным:**

- предложение без цены («ціна за запитом») отбрасывается — сравнивать нечего;
- валюта берётся из символа в ячейке цены (`грн`→UAH, `$`→USD, `€`→EUR);
- заголовки `Accept-Language` и `Referer` обязательны, иначе WAF отдаёт
  JS-челлендж; не заявлять `br` без пакета brotli;
- отсутствие таблицы предложений — это `ParseError` («антибот или изменилась
  вёрстка»), а не пустой результат: пользователю нельзя показывать «нет
  конкурентов», когда мы просто не смогли распарсить страницу.

**Приёмка:**

- [ ] по эталонным номерам (`701807101` VW, `1K0129620D` VW, `93818439` IVECO)
      возвращается ≥ 5 предложений и марка совпадает с ожидаемой;
- [ ] тот же номер **без** переданного бренда, но с названием товара, даёт ту
      же марку, что и с брендом;
- [ ] при недоступности avto.pro API отдаёт 502 с текстом, а не 500;
- [ ] когда номер не найден — 404 с понятным текстом, а не пустой 200.

> ❓ Решить: сколько страниц ленты тянуть. Сейчас 2 — этого хватает на сводку,
> но минимальная цена может быть на 3-й странице, если лента отсортирована не
> по цене. Нужно проверить сортировку ленты и зафиксировать здесь.

## 4. Сопоставление товаров (`services/matching.py`)

Используется при сравнении товара с предложениями других продавцов prom.ua.
Три уровня, в порядке доверия:

1. **model_id** — собственный идентификатор prom.ua, точное совпадение;
2. **sku** — артикул, точное совпадение;
3. **fuzzy** — по названию: токены без стоп-слов, оценка = 0.5·Jaccard +
   0.5·containment, порог `similarity_threshold` (0.55).

Fuzzy отклоняется, если бренды несовместимы (оба известны и разные) или
названия указывают на противоположные стороны: лівий/правий,
передній/задній, верхній/нижній. Из каждого продавца берётся самое дешёвое
предложение, список ограничен `max_sellers` (10).

**Приёмка:** левая деталь никогда не матчится с правой; товар не матчится сам
с собой и с собственным продавцом; результат отсортирован по цене.

> ❓ Решить: порог 0.55 подобран на глаз. Нужен размеченный набор из ~50 пар
> «одно и то же / разное» с реального каталога, чтобы порог стал измеримым.

## 5. Общее правило для всех парсеров

Парсер чужого сайта ломается не «если», а «когда». Поэтому:

- разбор верстки изолирован в `parser.py`, сеть — в `client.py`/`gateway.py`;
- любое изменение структуры страницы обязано давать `ParseError` с
  человеческим текстом, а не пустой список;
- тесты парсеров работают на сохранённых фикстурах, а **приёмка — на живом
  запросе**: зелёные unit-тесты не доказывают, что источник не изменился.
