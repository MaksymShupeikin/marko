### 0.4. Определения и обозначения

Используются сквозно во всём документе.

```
i          — индекс позиции каталога заказчика (SKU), i = 1..N, N = 4901
j          — индекс предложения конкурента
t          — tier: {OEM, OES, AM_A, AM_B, KEMP, USED, UNKNOWN}
p_i        — текущая цена заказчика по позиции i
c_j        — цена предложения j
s(j)       — продавец предложения j
g(s)       — seller group (после дедупликации)
t(j)       — tier предложения j
O_i        — множество предложений, найденных по позиции i
E_i ⊆ O_i  — предложения с exact OE match
F_i ⊆ E_i  — прошедшие все фильтры (new, independent, valid price, normalized qty)
n_i        — |{ g(s(j)) : j ∈ F_i }|  — число независимых seller groups
k_t        — коэффициент премии tier t относительно базового tier (KEMP)
ĉ_j        — цена j, приведённая к уровню заказчика: ĉ_j = c_j / k_{t(j)}
M_i        — оценка рыночного уровня по позиции i (робастная)
q_i        — темп продаж, шт/мес (заказчик: 3-5 в среднем)
V_i        — упущенная выгода в месяц по позиции i
```

### 2.2. Для каждого требования установи четыре факта

```
CODE     : файл:строка, где требование реализовано (или NONE)
TEST     : файл:строка теста, который его проверяет (или NONE)
FIXTURE  : тест на РЕАЛЬНЫХ данных или на синтетике?
EVIDENCE : артефакт замера, где видно, что оно сработало на живых данных
```

Статус требования:

```
IMPLEMENTED_VERIFIED   : CODE ≠ NONE ∧ TEST ≠ NONE ∧ FIXTURE=real ∧ EVIDENCE ≠ NONE
IMPLEMENTED_UNVERIFIED : CODE ≠ NONE ∧ (TEST = NONE ∨ FIXTURE=synthetic)
PARTIAL                : реализовано с сужением области действия — опиши сужение
MISSING                : CODE = NONE
CONTRADICTED           : код делает обратное README — ВЫСШИЙ ПРИОРИТЕТ
```

**Критично:** статус `IMPLEMENTED_VERIFIED` присваивается только после того,
как ты ПРОЧИТАЛ ТЕЛО теста и убедился, что ассерт проверяет именно это
требование. Название теста не является доказательством. Тест, который
проверяет, что функция не падает, не проверяет её корректность.

### 3.1. Робастная оценка рыночного уровня

Восстанови из кода фактическую формулу оценки рынка. Ожидается робастная
статистика (IQR, не среднее). Запиши её явно в нотации:

```
Пусть Ĉ_i = { ĉ_j : j ∈ F_i }  — приведённые цены, |Ĉ_i| = n_i

Q1 = quantile(Ĉ_i, 0.25),  Q3 = quantile(Ĉ_i, 0.75),  IQR = Q3 - Q1
Отсев выбросов: [Q1 - 1.5·IQR, Q3 + 1.5·IQR]
M_i = median(Ĉ_i после отсева)
```

Проверь численно следующие свойства. Для каждого — напиши временный скрипт
в scratchpad и получи числа, не рассуждай умозрительно.

```
P1  ИНВАРИАНТНОСТЬ К SUNK COST
    ∀ cost: M_i(данные, cost) = M_i(данные, cost')
    Рекомендуемая цена не зависит от закупочной цены.
    Тест на это заявлен существующим — найди его, прочитай ассерт,
    убедись, что он проверяет цену, а не только отсутствие исключения.

P2  МОНОТОННОСТЬ
    Добавление наблюдения c > M_i не должно уменьшать M_i.
    Добавление c < M_i не должно увеличивать M_i.
    Проверь на реальных Ĉ_i из артефактов.

P3  УСТОЙЧИВОСТЬ К ВЫБРОСУ (breakdown point)
    Подмени одно наблюдение на 100× — насколько сдвинется M_i?
    Для медианы при n≥3 сдвиг должен быть ограничен.
    ПРИ n=2 медиана = среднее двух → breakdown point = 0.
    Это критическая точка: при n=2 IQR-отсев невозможен вообще
    (Q1 и Q3 вырождены). Проверь, что код это осознаёт.

P4  ПОВЕДЕНИЕ ПРИ МАЛЫХ n
    Прогони формулу при n = 0, 1, 2, 3 на реальных данных.
    n=0 → должно вернуть insufficient_data, НЕ 0, НЕ None-в-расчёте
    n=1 → single_market_reference, НЕ уверенная рекомендация
    n=2 → low_confidence
    Проверь, что деления на n нигде не происходит без защиты.

P5  DECIMAL, НЕ FLOAT
    grep на float-арифметику в денежных путях. Найди любое место,
    где Decimal смешивается с float — это источник копеечных дрейфов
    и невоспроизводимости.

P6  ИДЕМПОТЕНТНОСТЬ
    Двукратный прогон на одном входе даёт побитово равный выход.
    Проверь на сортировке при равных ключах — нестабильная сортировка
    даёт разный порядок и разные "топ-N упущенной выгоды".

P7  DEADBAND
    |рекомендация - p_i| / p_i < deadband → рекомендация НЕ выдаётся.
    Найди фактическое значение deadband в конфиге. README требует 3-5%.
    Проверь граничные случаи: ровно 3%, 2.999%, 5.001%.

P8  COMPETITIVE BUFFER
    market_target = lower_market_reference × (1 - competitive_buffer)
    Проверь: что именно взято как lower_market_reference — минимум?
    Q1? нижняя граница доверительного интервала? README говорит
    "lower_market_reference" без определения — это амбивалентность
    спецификации, зафиксируй её как дефект README, а не кода.
```

### 3.2. Аудит tier-коэффициентов и partial pooling

Это самая опасная математика в проекте: ошибка здесь не падает, а тихо
портит каждую цену.

Восстанови из кода фактическую модель. Ожидается shrinkage-оценка вида:

```
Для tier t наблюдаются парные отношения:
    r_m = c_m^{(t)} / c_m^{(KEMP)}   для позиций m, где есть обе цены

Локальная оценка:      k̂_t^{local} = median{ r_m }
Глобальная оценка:     k̂^{global}  = median по всем tier'ам (prior)
Shrinkage:             k̂_t = w_t · k̂_t^{local} + (1 - w_t) · k̂^{global}
                       w_t = n_t / (n_t + λ)
```

Проверь:

```
T1  Найди фактическое λ. Оно должно быть в конфиге, не в коде.
    При n_t → 0:  w_t → 0,  k̂_t → prior. Проверь численно.
    При n_t → ∞:  w_t → 1,  k̂_t → local.  Проверь численно.

T2  ПАРНОСТЬ. Отношение r_m должно считаться по ОДНОЙ И ТОЙ ЖЕ позиции.
    Если код делит медиану цен tier A на медиану цен tier B по разным
    наборам позиций — это грубая ошибка (симпсоновский парадокс):
    смешение состава позиций даёт коэффициент, не имеющий смысла.
    Это надо проверить чтением кода И численно на артефактах.

T3  ЛОГАРИФМИЧЕСКАЯ ШКАЛА. Отношения цен мультипликативны.
    Медиана отношений ≠ отношение медиан. Усреднение отношений в
    линейной шкале асимметрично: 0.5 и 2.0 дают среднее 1.25, а не 1.0.
    Проверь, работает ли код в log-пространстве. Если нет — посчитай
    величину смещения на реальных данных и покажи числом.

T4  ОБРАТИМОСТЬ. k_{A→B} должно равняться 1 / k_{B→A}.
    Проверь численно на всех парах tier'ов.

T5  ТРАНЗИТИВНОСТЬ. k_{A→C} ≈ k_{A→B} · k_{B→C}.
    Расхождение > 15% означает несогласованную систему коэффициентов.

T6  САНИТИ-ГРАНИЦЫ (из хендоффа):
        OEM / AM_B  ожидается 2.0 – 3.0
        OES / AM_B  ожидается 1.7 – 2.2
    Значение вне [1.2, 5.0] = грязь в данных (намешаны tier'ы, б/у,
    комплекты), а НЕ открытие. Проверь, есть ли в коде такая проверка
    и что происходит при её нарушении. Должен быть отказ, не warning.

T7  ПОВЕДЕНИЕ ПРИ ПУСТОМ brands.yaml (текущее состояние!).
    Все не-KEMP → UNKNOWN → k_UNKNOWN не определён.
    Проверь: код отказывается считать (правильно) или подставляет
    k=1.0 по умолчанию (катастрофа — сравнение оригинала с KEMP в лоб).
    ЭТО САМАЯ ВАЖНАЯ ПРОВЕРКА ВСЕЙ ФАЗЫ 2.
```

```

```

## 6. ФАЗА 5 — ПЕРЕОПРЕДЕЛЕНИЕ ЗАДАЧИ: ДЕТЕКЦИЯ НЕДООЦЕНКИ

**Цель:** проверить гипотезу, что при тонких данных система может быть
полезна в формулировке «где я сильно дешевле рынка», даже когда не может
назначить цену.

### 6.1. Обоснование

Заказчик формулировал задачу как «говорить, где поднимать, если сильно
дешевле рынка» и «фильтр по величине изменения цены, чтобы начать менять
цены с более необходимых». Это **детекция**, а не **оценка**.

Статистически это разные задачи с разной требовательностью к данным:

```
ОЦЕНКА:   нужен M_i с малой дисперсией → требует n ≥ 3
ДЕТЕКЦИЯ: нужен ответ на вопрос p_i ≪ M_i → достаточно n = 2
          при большом разрыве и согласованности наблюдений
```

### 6.2. Формальное решающее правило

Определи:

```
Отношение недооценки:   R_i = M_i / p_i
Согласованность:        для n_i = 2 определим
                        d_i = |ĉ_(1) - ĉ_(2)| / min(ĉ_(1), ĉ_(2))
```

Правило (все пороги — в конфиг, не в код):

```
SIGNAL_UNDERPRICED(i) :=
    n_i ≥ 3  ∧  R_i ≥ θ_3
  ∨ n_i = 2  ∧  R_i ≥ θ_2  ∧  d_i ≤ δ
  ∨ n_i = 1  →  НИКОГДА не сигнал; только manual_review_required

Предлагаемые стартовые значения (подлежат калибровке в фазе 6):
    θ_3 = 1.25     θ_2 = 1.60     δ = 0.25
```

Обоснование θ_2 > θ_3: при n=2 дисперсия оценки выше, порог должен
компенсировать. Обоснование δ: два наблюдения, расходящиеся между собой
больше чем на 25%, вероятно принадлежат разным tier'ам или содержат
брак данных — согласованности нет, сигнал не выдаётся.

### 6.3. Обязательные условия (не ослаблять)

U1  Tier-приведение остаётся ОБЯЗАТЕЛЬНЫМ. Без brands.yaml сигнал

Глазная проверка обязательна: возьми 30 сигналов, открой ссылки на
конкурентов, ответь по каждому «та же деталь того же уровня — да/нет».
Без этого precision неизвестен, а правило нельзя выпускать.

## 7. ФАЗА 6 — ЭКОНОМИЧЕСКАЯ МОДЕЛЬ ЦЕННОСТИ

**Цель:** перевести технические метрики в деньги. Это то, что показывают
заказчику, и то, по чему сортируется отчёт.

### 7.1. Модель упущенной выгоды

```
Для позиции i с сигналом недооценки:
    Δp_i = M_i·(1 - buffer) - p_i          — прирост цены
    V_i  = Δp_i · q_i                       — упущенная выгода в мес.
```

Проблема: `q_i` (темп продаж) неизвестен по позициям. Заказчик назвал
средние 3–5 шт/мес, но это среднее по ассортименту, и оно плохо
согласуется с существованием неликвида («купили 8 лет назад и не
продали»). Это внутреннее противоречие входных данных.

Следовательно:

```
E1  Установи, есть ли в xlsx-выгрузке данные о продажах или дате
    последней продажи. Проверь фактически по
    outputs/metis_catalog_number_nature_20260724/catalog_rows.json
    и по коду импорта backend/src/marko/services/xlsx_catalog.py
    (87 колонок — перечисли их и найди всё, относящееся к продажам).
E2  ЕСЛИ данных о продажах нет — V_i не вычислим, и ранжирование
    «по деньгам» невозможно. Тогда допустимы только суррогаты,
    и каждый должен быть явно помечен как суррогат:
       V_i^{surrogate} = Δp_i            (ранжирование по абсолютному
                                          приросту, без учёта оборота)
       V_i^{relative}  = Δp_i / p_i      (по относительному)
    Заяви это ограничение прямо: система ранжирует по потенциалу
    цены, а не по деньгам, пока нет данных о продажах.
E3  Сформулируй вопрос заказчику: есть ли выгрузка продаж или дата
    последней продажи по позиции. Это дешёвый запрос с высокой
    отдачей — он включает и ранжирование по деньгам, и автоматическое
    определение неликвида (сейчас помечается вручную).
```

### 7.2. Совокупная оценка ценности продукта

```
Пусть:
    N_signal  — число позиций каталога с сигналом (из фазы 5, с ДИ)
    V̄         — медианный прирост цены по сигнальным позициям
    q̄ = 3..5  — темп продаж (диапазон заказчика)

Годовая ценность (интервальная оценка, не точечная):
    V_year ∈ [ N_signal · V̄ · 3 · 12 ,  N_signal · V̄ · 5 · 12 ]
```

Посчитай с нижней и верхней границей ДИ по N_signal. Результат — интервал,
и его надо предъявлять как интервал. Точечная оценка здесь была бы
недобросовестной: она создаёт впечатление точности, которой нет.

Сопоставь с ценой договора 1500 €. Это единственная метрика, которая
имеет значение для заказчика, и её надо получить честно, включая случай,
когда она выходит неутешительной.

### 7.3. Двухрежимность и неликвид

```
E4  Проверь реализацию режима «неликвид»: как позиция помечается
    stale, есть ли автоматический признак, что происходит при
    отсутствии себестоимости (README: margin_safety=unknown +
    manual_review_required).
E5  Проверь разделение: ДАВНОСТЬ лежания управляет режимом
    (вверх/вниз), ЗАКУПОЧНАЯ ЦЕНА не входит в целевую цену, а только
    в порог авторизации продажи ниже себестоимости.
    Формулировка заказчика «купили 8 лет назад — продаём в минус»
    использует давность, а не себестоимость, и она СОВМЕСТИМА
    с инвариантом sunk cost. Убедись, что код это разделяет,
    а не смешивает.
E6  Заказчик закупочные цены не даёт. Значит below-cost авторизация
    и «мин. маржа ±20%» непроверяемы системой. Зафиксируй, какая
    часть логики себестоимости мертва, и что нужно уточнить
    у заказчика (от чего считается ±20% — от цены продажи или от
    закупки; сейчас формулировка неоднозначна).
```

## 10. ОБЯЗАТЕЛЬНАЯ САМОПРОВЕРКА (ВАРИАЦИЯ)

Выполняется ПОСЛЕ формирования отчёта, ДО его выдачи. Цель — не допустить
ошибок в продакшн-выводах.

### 10.1. Проход A — арифметическая перепроверка

Пересчитай каждое число в отчёте вторым независимым способом:
- доли — из абсолютных количеств заново;
- медианы — сортировкой вручную на малых наборах;
- коэффициенты — обратным умножением (k·базовая = исходная?);
- ДИ — по альтернативной формуле (нормальное приближение против Уилсона).

Расхождение > 1% в любом числе → найди причину, исправь, пометь.

### 10.2. Проход B — вариация допущений

Для каждого ключевого вывода проверь устойчивость к изменению допущений:

```
- Изменится ли вывод при θ_2 = 1.4 вместо 1.6?
- Изменится ли при λ (shrinkage) в 2 раза больше/меньше?
- Изменится ли при deadband 3% вместо 5%?
- Изменится ли при исключении самой большой позиции из выборки?
  (jackknife — убери по одной позиции из 30, посмотри разброс медианы)
```

Вывод, который переворачивается от изменения одного порога, должен быть
помечен как НЕУСТОЙЧИВЫЙ, а не подан как факт.

### 10.3. Проход C — состязательное чтение

Перечитай собственный отчёт в роли скептика, задача которого — его
опровергнуть. Для каждого утверждения:

```
- Есть ли под ним конкретное число и путь к файлу?
- Отличается ли факт от предположения текстуально?
- Нет ли обобщения с 30 SKU на 4901 без указания ДИ?
- Нет ли фразы "вероятно/скорее всего" в разделе с числами?
- Нет ли утверждения о работоспособности, опирающегося только на
  название теста, а не на прочитанный ассерт?
- Не выдумано ли где-то доменное знание (tier бренда, структура Prom)?
```

Каждое утверждение, не прошедшее эти вопросы, либо переписывается,
либо удаляется.

### 10.4. Проход D — проверка на нарушение ограничений раздела 0

```
CONSTRAINT_2: есть ли места, где проверка была выборочной вместо полной?
CONSTRAINT_3: остались ли TODO/предположения?
CONSTRAINT_5: не выдуман ли где-то tier бренда?
CONSTRAINT_6: не изменён ли код?
CONSTRAINT_7: не было ли сетевых запросов?
CONSTRAINT_8: не появились ли манифесты и governance-структуры?
```

Нарушение любого — вернуться и переделать соответствующий раздел.
