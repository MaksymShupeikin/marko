# Что можно выжать без заказчика — разбор пяти рычагов, 2026-08-07

Новых данных от заказчика не будет. Проверено пять предложенных рычагов внутри
уже имеющихся источников. Три оказались построенными, один построен наполовину
и достроен, а у главного обнаружилось, что его центральная посылка неверна.

| | |
|---|---:|
| позиций каталога | 4663 |

## Главная находка: kemp.ua не может открыть pricing, и это сделано намеренно

Посылка пункта «полный harvest kemp.ua — добить OE там, где сайт знает»
**не подтвердилась**. Проверено файловым расчётом, без базы: `plan_identity`
по двум справочникам с файлом сайта и без него даёт **одни и те же статусы**.

Датасет на момент проверки — ревизия 2026-08-06 (2372 строки):

| | без `kemp_site_numbers.csv` | с ним |
|---|---:|---:|
| `OE_CONFIRMED` | 5219 | 5219 |
| `MPN_ONLY` | 1954 | 1954 |
| `UNRESOLVED` | 20 | 20 |
| связей в графе | 3420 | **3435** |

Причина в `identity_graph.yaml:21-23` и в `_asserted_numbers`
(`services/catalog_identity_reparse.py:1181`): `KEMP_SITE` объявлен
`status: REVIEW` при `asserts_oe: true`. Подписи полей на карточке недостоверны
(поле «ОЕ номер» на aftermarket-позициях содержит артикул, и наоборот),
контрольной проверки нет. Поэтому связь, рождённая сайтом, **рождается REVIEW и
повышается до CONFIRMED человеком или совпадением с другим источником, но не
сама собой**.

Архивный план от 2026-08-05 показывал обратное — с сайтом `OE_CONFIRMED` 5498
против 5222 без него, то есть +276 позиций. Это была не польза, а дефект:
комментарий в `assertion_is_eligible` называет его прямо — прежнее правило
`len(sources) > 1` засчитывало пару `KEMP_SITE` + `KEMP_REFERENCE_ARTICLE` и
могло заполнить OE каталога неподписанным артикулом с карточки. Конфиг с тех
пор не менялся (`116a0b8d…` в обоих замерах), изменился код: sha
`catalog_identity_reparse.py` в архиве `319b0756…`, в рабочем дереве другой.

**Вывод.** Те 1954 кода нельзя открыть данными, которые у нас есть. Их открывает
только человек, подтверждающий REVIEW-связь. Это ровно то разделение, которое
заказчик и задал: «MPN_ONLY без подтверждённого OE — только discovery/manual
review».

Полный harvest всё равно имеет смысл, но его продукт другой: **больше и лучше
материала для ревью** — REVIEW-связи с URL карточки и провенансом изображения,
плюс публичные номера для retrieval-ключей. Не больше позиций с ценой.

## Что уже было построено

**Selective cross → pricing только с гейтами.** `declared_widenings`
(`pricing_runs.py:866`) отдаёт только `role == "CROSS"` и
`confidence == "confirmed"`; у CROSS-ключей `pricing_primary=False`; шлюз тратит
кросс только когда первичный запрос вернул меньше `min_independent_sellers`
независимых продавцов; граница `_offer_search_identity` роняет прогон, если
строка заявляет незамороженный кросс.

**Honest states.** `RecommendationAction` = `RAISE / HOLD / LOWER /
MANUAL_REVIEW / INSUFFICIENT_DATA`, плюс `ComparabilityVerdict.INSUFFICIENT_DATA`
и 13 кодов `MANUAL_*`. Позиция без публичного ключа не выпадает молча:
`market_collection.py:4678` ставит `offers = []` и добавляет причину
`CUSTOMER_IDENTITY_MISSING`, движок на пустом рынке отдаёт `INSUFFICIENT_DATA`.

**Store-sync четырёх витрин.** Подсистема есть целиком — воркер, очередь, лизы,
API. Это операционный прогон, а не код.

## Что достроено: ярус retrieval-only запросов

`build_public_search_keys` строил упорядоченный список
OE → confirmed CROSS → PUBLIC_MPN → PART_NUMBER, но `declared_widenings`
фильтровал его до confirmed CROSS, и ключи `PUBLIC_MPN` / `PART_NUMBER`
**строились и никогда не отправлялись**.

Открыты отдельным ярусом, физически неспособным дать цену:

- `QueryInput.discovery_queries` — второй замороженный список рядом с
  `fallback_queries`. Два списка, а не один: у них разный правовой статус.
  Номер, уже замороженный как confirmed cross, в слабый список не попадает.
- Шлюз пробует их **после** кроссов и метит строки через `found_by_query`.
- `_offer_search_identity` получил третий исход: номер из замороженного
  `discovery_queries` — законное приобретение, но **не** утверждение
  идентичности, поэтому строка возвращает первичный OE и проверяется против
  него. Номер, которого нет ни в одном из двух списков, по-прежнему роняет
  прогон.

Дефект шва, найденный при ревью и починенный тестом-первым: порог
`min_independent_sellers` передавался в шлюз только при наличии confirmed
крестов, а `_extend_via_declared_widenings` выходит сразу при
`min_independent_sellers <= 0`. Строка с публичным MPN и без кросса — случай
частый, а не краевой; для неё ярус был бы заморожен в хэш и никогда не запущен.

**Честно об эффекте.** Это не поднимает число позиций с ценой. Для
`OE_CONFIRMED` первичный OE уже даёт медиану 53 удержанных продавца.
Производитель, который заполняет список, живёт в pricing-пути
(`pricing_runs.py`), а тот отказывает `MPN_ONLY` строкам на
`customer_identity_available` — значит новый ярус сегодня работает на
`OE_CONFIRMED` строках. Чтобы он дошёл до 1788 `MPN_ONLY`, точка входа
discovery (`catalog_discovery._collect_live`) должна получить `identity_status`;
это отдельный шаг.
