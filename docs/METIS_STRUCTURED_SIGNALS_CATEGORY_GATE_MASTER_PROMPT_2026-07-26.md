## 1. ВЕРИФИЦИРОВАННОЕ ТЕКУЩЕЕ СОСТОЯНИЕ

### 1.1. `CandidateItem` сейчас (подтверждено чтением `candidate_selection.py:121-129`)

```python
@dataclass(frozen=True, slots=True)
class CandidateItem:
    seller_id: str
    seller_name: str
    title: str
    description: str | None
    article_field: str | None
    brand: str | None
    price: Decimal
    condition: str | None = None
```

Полей `category_id, fitment, vehicle_generation, year_from, year_to, side,
position, model_id` — нет.

### 1.2. Что реально отдаёт Prom (подтверждено чтением `parser_models.py:13-51`)

`_FIELDS_PATH_MAP` — единственный источник истины о том, откуда берётся
каждое поле `Product`:

| Поле `Product` | JSON-путь в Apollo cache | Нативность |
|---|---|---|
| `category_id` | `categoryId` | **нативное поле Prom**, ожидается всегда присутствующим для карточки товара |
| `brand` | `manufacturerInfo.name` | **нативное**, уже используется в `CandidateItem.brand` |
| `model_id` | `model.id` (fallback `newModelId`) | **нативное**, комментарий в коде: "может отсутствовать" |
| `characteristics` | `characteristics` (верхний уровень) | **нативное поле присутствует**, но точная структура (список пар атрибут/значение или что-то иное) НЕ проверена на реальном ответе — это делает WP-0 |
| `fitment`, `vehicle_generation`, `year_from`, `year_to`, `engine`, `body_variant`, `side`, `position`, `condition` (в `Product`, не путать с `CandidateItem.condition`), `package_quantity` | все под префиксом `comparisonEvidence.*` | **не нативные Prom-поля**. Комментарий в коде прямо говорит: "Additive post-parse/enrichment boundary. The frozen network parser may leave every field below absent" |

### 1.3. Подтверждённый факт: `comparisonEvidence.*` никогда и никем не заполняется

```bash
grep -rn "comparisonEvidence" backend/src
```
даёт единственное место использования — `offer_identity.py:194-195`, и то
только оборонительное чтение (`_nested(raw_offer, "comparisonEvidence",
"oeRaw")`), которое вернёт `None`, если ключа нет. **Ни один модуль не
пишет** в `comparisonEvidence`. Условие "это поле, которое парсер может
оставить пустым" в реальности означает "это поле, которое парсер
оставляет пустым всегда, потому что Prom никогда не кладёт такой ключ в
свой Apollo-кэш — это имя придумано в схеме `Product` заранее, под
будущую интеграцию, которой ещё не существует".

**Вывод:** формулировка задачи "ворота 6/8 сначала смотреть на
структурные поля" в буквальном виде (`fitment`, `vehicle_generation`,
`side`, `position` и т.д.) сегодня не может быть реализована как
"использовать существующие данные Prom" — этих данных с гарантией нет.
Единственный шанс получить `side`/`position`/`vehicle_generation`/`year_*`
не через regex — это либо (а) распарсить `characteristics`, если он
структурно содержит такие атрибуты (гипотеза, не факт — проверяется в
WP-0), либо (б) не делать этого вовсе и оставить ворота 6/8 работать
через regex, как сейчас, задокументировав `comparisonEvidence.*` как
`BLOCKED_NO_DATA_SOURCE`.

### 1.4. Что уже подтверждено пригодным без всяких оговорок

`category_id` — нативное поле Prom, физически долетает до `product` dict
в `catalog_discovery.py` (переменная `product`, из которой уже читаются
`name, sku, seller_name, brand, description, condition` — см.
`catalog_discovery.py:480-513`), но не передаётся в `CandidateItem`.
`model_id` — аналогично нативно, но не передаётся. Это единственные два
поля из первоначального списка задачи, по которым не требуется WP-0
для подтверждения существования данных (нативность подтверждена самим
`_FIELDS_PATH_MAP`) — WP-0 для них нужен только чтобы подтвердить
**заполненность** (как часто это поле реально не `None` на живых данных),
не факт существования пути.

## 2. МАТЕМАТИЧЕСКАЯ МОДЕЛЬ

### 2.1. Категорийные ворота — два режима, формально

Пусть `Q` — один discovery-run (один поисковый запрос, например
`7E5827505A`), `N` — число кандидатов в `Q` с непустым `category_id`,
`c₁,...,c_N` — их значения `category_id`.

**Режим A (allowlist, авторитетный, приоритетный если доступен).**
Пусть `A ⊂ ℤ` — конфигурируемое множество id категорий, относящихся к
автозапчастям (дерево категорий Prom, полученное отдельным запросом —
WP-2). Тогда:
```
gate_category(candidate) =
    SKIP("CATEGORY_NOT_AUTOPARTS")  если candidate.category_id ∉ A
                                     и candidate.category_id ≠ None
    PASS                             если candidate.category_id ∈ A
    PASS + flag("CATEGORY_UNKNOWN")  если candidate.category_id = None
```
`None` не скипается — отсутствие данных не наказывается (тот же fail-open
принцип для отсутствующих данных, что уже применён к воротам 8 в базовой
цепочке).

**Режим B (majority-vote, эвристический fallback — используется только
для тех category_id, которых нет в `A`, ЛИБО если `A` вообще недоступен,
т.е. WP-2 заблокирован отсутствием источника дерева категорий).**

Определим моду выборки:
```
mode(Q) = argmax_{v} |{i : cᵢ = v}|
majority_share(Q) = |{i : cᵢ = mode(Q)}| / N
```
Решающее правило:
```
IF N < N_min (например, N_min = 5, конфигурируемо)
    → gate_category = PASS (недостаточно данных для голосования, no-op)
IF majority_share(Q) < τ (например, τ = 0.6, конфигурируемо)
    → gate_category = PASS (нет уверенного большинства — не голосуем)
IF candidate.category_id ≠ mode(Q)  И  majority_share(Q) ≥ τ  И  N ≥ N_min
    → SKIP("CATEGORY_OUTLIER_MAJORITY_VOTE")
ELSE
    → PASS
```
**Важное ограничение** (обязательно к соблюдению): Режим B — это
доказательство по большинству голосов внутри ОДНОГО запроса, не
абсолютная истина о категории. Он обязан идти вторым приоритетом после
Режима A, и при их одновременной применимости результат Режима A
всегда главенствует (не голосуем большинством там, где есть авторитетный
список). Комбинированное правило:
```
gate_category(candidate, Q, A) =
    result_A(candidate, A)              если A ≠ ∅ и candidate.category_id
                                          определённо принадлежит домену,
                                          покрываемому A (т.е. A построен
                                          полно, не частично)
    result_B(candidate, Q)              иначе (A недоступен/неполон)
```
Если `A` только частично покрывает дерево категорий Prom — не притворяться,
что оно полное; в этом случае гейт обязан идти в режиме B, а не
вычислять ложноположительный `CATEGORY_NOT_AUTOPARTS` для категорий,
которые просто не попали в неполный allowlist.

### 2.2. Место гейта в цепочке — обоснование по критерию §2.2 предыдущего документа

Категорийный гейт — дешёвый (сравнение целого числа с множеством/модой,
O(1) или O(log|A|)) и высокоселективный против случайных текстовых
коллизий артикулов (ровно случай "накладка для бассейна Emaux" —
это не редкость, это системный риск любого текстового поиска по
общему маркетплейсу). По формуле §2.2 предыдущего документа
(`E[C] = Σ cᵢ·Π(1-sⱼ)`, порядок по убыванию `sᵢ/cᵢ`) — это ставит
категорийный гейт сразу после ворот 1-2 (own_seller, dismantler) и
**перед** OEM identity (ворота 5), т.к. нет смысла тратить regex/OEM-поиск
на кандидата, который в принципе не автозапчасть. Новый порядок цепочки:

```
1. own_seller
2. dismantler
3. category_domain   ← НОВОЕ
4. condition
5. remanufactured
6. oem_identity (+ oem_stuffing)
7. variant
8. package
9. applicability
10. tier
11. price_anomaly
```
(нумерация сдвинута на +1 от исходной; reason-коды существующих ворот не
переименовываются, меняется только их порядковый номер в `passed_gates`).

### 2.3. Приоритет структурных полей над regex — формальное правило

Для каждой оси `axis ∈ {side, position, vehicle_generation, year, brand,
model}` определим функцию выбора значения:
```
value(axis, candidate) =
    normalize_structured(candidate.structured[axis])
        если candidate.structured[axis] ≠ None
        И normalize_structured(...) успешно распознаёт значение
        (см. CONSTRAINT_4 — при нераспознанном значении НЕ считать None,
        а поднимать явный BLOCKED/ошибку валидации конфига, потому что
        нераспознанное структурное значение — это признак того, что
        схема поменялась, а не что данных нет)
    regex_extract(axis, candidate.title)
        иначе (structured[axis] is None)
```
Это НЕ "структурное поле ИЛИ regex, выбираем более уверенный" — порядок
строго детерминирован (структурное всегда побеждает при наличии), потому
что структурное поле в системе Prom считается более достоверным
источником, чем эвристика по тексту заголовка. Если оба источника в
будущем окажутся заполнены и дадут разные значения — не молча брать
структурное, а завести `flag("STRUCTURED_REGEX_CONFLICT")` для
последующего аудита (это не блокирует вердикт, но помечает случай,
достойный ручной проверки словаря `applicability`/`variant_axes`).

   один.
3. Если источник найден — сохранить `A` в `config/` (не в коде), с
   человекочитаемыми названиями категорий рядом с id (для аудита).
4. Реализовать `_gate_category_domain` по формуле §2.1, вставить в
   цепочку на позицию 3 (после dismantler, до condition) — обновить
   `passed_gates` нумерацию и любые UI/тесты, завязанные на порядковый
   номер ворот (проверить Flutter `catalog_competitor_section.dart` —
   не завязан ли он на "Пройдено ворот: N" как на магическое число).

**Тесты:**
- Режим A: candidate.category_id ∈ A → PASS; ∉ A → SKIP; None → PASS+flag.
- Режим B (при A=∅ или неполном): N<N_min → PASS (no-op); N≥N_min и
  majority_share<τ → PASS (no-op); N≥N_min и majority_share≥τ и outlier
  → SKIP; сам mode-кандидат никогда не скипается сам собой.
- Вариация: все кандидаты имеют разный category_id (нет большинства) —
  gate не должен ничего скипать (не путать "нет большинства" с "все
  подозрительны").
- Вариация: ровно на границе `τ` (например majority_share == τ ровно).

**Стоп-гейт:** живой прогон на `7E5827505A` и на `2141006` — во втором
случае бассейновая накладка Emaux обязана получить `SKIP` (не `REVIEW`),
с указанием, каким именно режимом (A или B) это достигнуто, и числом
`majority_share`/принадлежностью `A`.

### WP-3. Заполнение и приоритет структурных полей в воротах 6 (variant) и 8 (applicability)

**Условие запуска:** только для полей, по которым WP-0 подтвердил
реальный источник данных (см. WP-1). Если WP-0 подтвердит, что ни
`side`, ни `position`, ни `vehicle_generation`, ни `year_from/to` не
доступны ни напрямую, ни через `characteristics` — этот WP закрывается
как `BLOCKED_NO_DATA_SOURCE` целиком, без "частичной реализации ради
видимости прогресса" (CONSTRAINT_3).

**Если данные найдены (например, через `characteristics`):**
1. Написать явный, задокументированный маппинг "имя атрибута Prom →
   нормализованное значение оси" (например `"Сторона" → side_axis`,
   `"Ліва" → "left"`), со списком всех встреченных в WP-0 сырых значений
   — не расширять этот список по догадке для значений, которых не было
   в эмпирических данных.
2. Реализовать `value(axis, candidate)` по формуле §2.3: структурное
   значение побеждает при успешном распознавании; при нераспознанном
   сыром значении — не fallback на regex молча, а поднять предупреждение
   уровня `details["structured_parse_error"]` и в этом конкретном случае
   явно откатиться на regex (это единственный легитимный сценарий
   отката: "формат неожиданный", а не "формат достоверный, но неудобный").
3. Добавить `flag("STRUCTURED_REGEX_CONFLICT")`, если оба источника дали
   разные нормализованные значения для одной оси (диагностика, не блокер
   вердикта).
4. Ворота 6 и 8 должны логировать в `details`, каким источником
   (`structured` | `regex` | `unknown`) был определён каждый axis/
   бренд/модель/поколение — обязательно для последующего аудита §2.3.

**Тесты:**
- Структурное поле присутствует и валидно → используется, regex не
  вызывается (проверить через mock/spy, что regex-ветка не исполнялась).
- Структурное поле отсутствует (`None`) → regex-ветка работает как
  раньше, старые тесты гейтов 6/8 не должны сломаться ни одним ассертом.
- Структурное поле присутствует, но нераспознанное сырое значение →
  `structured_parse_error` в `details`, фактическое решение — по regex.
- Конфликт: структурное = "left", regex по заголовку нашёл "правий" →
  `flag("STRUCTURED_REGEX_CONFLICT")`, итоговое значение — структурное.

**Стоп-гейт:** таблица "ось → доля кандидатов с валидным структурным
значением → доля конфликтов structured vs regex" на золотом наборе,
не менее 50 карточек с непустым `characteristics`.


## 5. МАТРИЦА ВАРИАЦИЙ (обязательна при закрытии WP-1/WP-2/WP-3)

| # | Вариация | Что проверяет |
|---|---|---|
| 1 | `category_id = None` у кандидата | fail-open, не SKIP |
| 2 | Все `category_id` в выборке `Q` идентичны кроме одного — ровно граничный `majority_share = τ` | строгость сравнения `≥` vs `>` |
