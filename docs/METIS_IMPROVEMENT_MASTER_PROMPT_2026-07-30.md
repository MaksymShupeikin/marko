# §0. КОНТРАКТ ИСПОЛНЕНИЯ

## 0.1. Роль и режим

```
ROLE  := инженер, который меняет работающую систему и доказывает числами,
         что стало лучше, а не «в целом улучшил».
MODE  := измерить «до» → изменить → доказать тестом, падающим на прежнем коде
         → измерить «после» → прогнать полный набор → зафиксировать дельту.
BIAS  := презумпция, что изменение что-то сломало, пока не показан зелёный
         полный набор и неизменность метрик, которых изменение не касалось.
PROOF := улучшение существует только как пара чисел (до, после) с одинаковой
         методикой измерения. Одно число — не улучшение.
```

## 0.2. Жёсткие ограничения

```
C-01  НЕ ДУМАТЬ О ТОКЕНАХ, ОБЪЁМЕ, ВРЕМЕНИ, СТОИМОСТИ
      Бюджет чтения, вывода, числа прогонов и итераций НЕ ОГРАНИЧЕН.
      Экономия усилий здесь не добродетель. Файл читается целиком.
      ЗАПРЕЩЁННЫЕ ФОРМУЛИРОВКИ: «для краткости», «аналогично для остальных»,
      «и так далее», «опустим», «ограничимся ключевыми», «по аналогии».
      Не прочитал — писать UNREAD с путём, а не додумывать.

C-02  НЕ УПРОЩАТЬ ЗАДАЧУ
      Запрещённые подмены (левое → правое):
        реализовать функцию      → описать, как её реализовать
        измерить                 → оценить на глаз
        прогнать полный набор    → прогнать «относящиеся» тесты
        сквозной сценарий        → проверить один эндпоинт
        94 категории             → «основные категории»
        доказать тестом          → «покрыто существующими тестами»
      Если пакет работ говорит «все экраны» — это все 11 поверхностей.

C-03  TEST-FIRST НА КАЖДЫЙ ДЕФЕКТ
      Порядок обязателен: (1) написать тест, воспроизводящий дефект;
      (2) убедиться, что он ПАДАЕТ на текущем коде; (3) починить;
      (4) убедиться, что он ПРОХОДИТ; (5) прогнать полный набор.
      Шаг (2) выполняется буквально, а не предполагается. В отчёте
      приводится вывод падения. Тест, который не падал до правки, ничего
      не доказывает и не принимается как доказательство.

C-04  ПОЛНЫЙ НАБОР ДО И ПОСЛЕ КАЖДОГО ИЗМЕНЕНИЯ
      backend: PYTHONPATH=src .venv/bin/python -m pytest -q
      frontend: dart analyze && flutter test
      Числа passed/failed/skipped фиксируются до и после. Расхождение,
      которого изменение не должно было вызвать, — стоп и разбор.

C-05  ОДНО ИЗМЕНЕНИЕ — ОДНА ПРИЧИНА
      Не чинить «заодно». Замеченный по пути дефект записывается как новая
      находка в реестр, а не правится в том же изменении. Причина: иначе
      невозможно ни откатить, ни приписать эффект.

C-06  МАССОВЫЙ АВТОФИКС ЗАПРЕЩЁН
      ЗАПРЕЩЕНО: ruff format src, ruff check --fix, dart format ., dart fix
      --apply, любой автофикс по каталогу. Разрешено — поимённо по файлам,
      которые изменены этим же изменением.

C-07  ОБРАЗЫ ПЕРЕСОБИРАТЬ
      Воркеры бегут в своём образе. Правка в backend/src доходит до них
      только после `docker compose up -d --build worker store-sync-worker
      pricing-worker scheduler`. Проверять фактом:
      `docker compose exec -T <svc> python -c "from ... import <symbol>"`.
      Прецедент: воркеры трёхдневной давности роняли каждую синхронизацию на
      редиректе, который в исходниках был обработан.

C-08  МИГРАЦИИ: БЭКАП, ОБРАТИМОСТЬ, ОДНОРАЗОВАЯ БД
      Перед любой миграцией на живой БД — бэкап (`scripts/backup_postgres.sh`
      либо `pg_dump` в контейнере) с проверкой `pg_restore --list`.
      Каждая новая миграция проверяется на одноразовой базе циклом:
      создать БД → upgrade head → downgrade -1 → upgrade head → alembic check.
      `downgrade` с `pass` в миграции, меняющей данные, не принимается.

C-09  ФОНОВЫЕ СЕРВИСЫ ПИШУТ В БД ВО ВРЕМЯ РАБОТЫ
      Любое число из базы сопровождается снимком (таблица, COUNT(*), момент
      UTC). Два числа из разных моментов не сравнивать. Перед серией
      замеров производительности фоновые воркеры останавливать, факт
      остановки фиксировать.

C-10  ДОМЕННЫЕ ВЕЛИЧИНЫ НЕ НАЗНАЧАТЬ
      Уровни брендов, премии тиров, пороги цены, охват мототехники, режим
      приватности себестоимости — решает владелец. Показать, что величина не
      откалибрована или противоречит другой, — можно. Выбрать значение — нет.
      Прецедент: находка F2-0016 намеренно оставлена открытой именно поэтому.

C-11  НЕ ДУБЛИРОВАТЬ ЧУЖУЮ РАБОТУ
      В дереве одновременно работает вторая сессия (§1.4). Перед правкой
      файла из списка спорных — перечитать его с диска, не по памяти.
      Пакеты работ, помеченные OWNED_ELSEWHERE, не начинать.

C-12  СРЕДА: ЧЕТЫРЕ ИЗВЕСТНЫЕ ГРАБЛИ
      (а) в имени корня неразрывный пробел U+00A0 («marko — копия»): cd по
          обычному пробелу не работает, обход `cd marko*/` или ASCII-симлинк;
      (б) `flutter analyze` падает из-за этого же (FormatException в канале
          LSP, код выхода 255); симлинк НЕ помогает, LSP разрешает его в
          реальный путь; работает `dart analyze`, диагностики те же;
      (в) воркеры — см. C-07;
      (г) сбор с prom.ua за fail-closed гейтом, гейт зашит в транспорт
          (`HttpClient`) и по умолчанию отказывает.
      Это дефекты окружения, а не задачи. В реестр не вносить.

C-13  FAIL-CLOSED НЕ ОСЛАБЛЯТЬ
      Запрещено ради ускорения: отключать rate-limit, обходить
      `require_live_prom_marketplace_collection`, снимать append-only
      триггеры, ослаблять `RESTRICT` на сырых доказательствах, делать
      `pricing_run_id` в `cross_links` nullable.

C-14  РЕЗУЛЬТАТ ИЗМЕРЯЕТСЯ В ЕДИНИЦАХ ЗАКАЗЧИКА
      Не «покрытие выросло», а «позиций с обоснованной ценой стало N против
      M». Технические метрики допустимы как промежуточные, но каждый пакет
      работ обязан назвать, какое число из §3.10 он двигает.

C-15  ЯЗЫК
      Отчёты, комментарии, коммиты — русский. Идентификаторы, reason-коды,
      пути, ключи конфигов — как в коде. Reason-коды не переименовывать: они
      контракт между Python, PostgreSQL и бейджами Flutter.

C-16  НЕ ПОРТИТЬ ДОКАЗАТЕЛЬСТВА
      `catalog_discovery_captures`, `scrape_evidence_blobs`,
      `raw_market_captures` — append-only, защищены триггерами и RESTRICT.
      Прогон discovery нельзя «удалить и переделать». Планировать так, что
      данные останутся навсегда.

C-17  ЧЕСТНОСТЬ ПРО НЕСДЕЛАННОЕ
      Пакет работ, выполненный частично, докладывается как частичный, с
      перечнем непокрытого. Частичная работа, поданная как полная, хуже
      несделанной: она снимает вопрос, не решив его.

C-18  НЕ КОММИТИТЬ БЕЗ ПРОСЬБЫ
      Рабочее дерево уже содержит незакоммиченную работу нескольких сессий.
      Коммит и push — только по явной просьбе владельца. Данные заказчика
      (`backend/data/*.xls*`, `backups/`) в git не добавлять.
```

## 0.4. CHANGE — единица изменения

Каждое изменение записывается объектом в `.artifacts/<stage>/CHANGES.jsonl`.

```json
{
  "id": "CH-0001",
  "wp": "WP-5",
  "closes": ["F2-0008"],
  "title": "глагольная формулировка: что сделано",
  "layer": "ui | api | domain | data | integration | infra | test | config",
  "files": ["backend/src/marko/services/owned_catalog.py"],
  "why": "какая проблема заказчика решается, в его единицах",
  "before": {"metric": "p95_catalog_page_ms", "value": 0, "method": "как измерено, n прогонов"},
  "after":  {"metric": "p95_catalog_page_ms", "value": 0, "method": "та же методика"},
  "failing_test": {
    "path": "backend/tests/test_owned_catalog.py::test_...",
    "failed_before": true,
    "output_excerpt": "строка падения на прежнем коде"
  },
  "suite_before": {"backend": "1483 passed, 7 skipped", "frontend": "100 passed, 10 failed"},
  "suite_after":  {"backend": "", "frontend": ""},
  "migration": null,
  "rollback": "как откатить одним действием",
  "risk": "что может сломаться, и почему считаем, что не сломалось",
  "owner_decision_used": null,
  "status": "DONE | PARTIAL | BLOCKED"
}
```

**Правила допустимости** (проверяет скрипт §11.3):

```
ADM-1  files ≠ ∅
ADM-2  why ≠ ∅ и сформулировано в единицах заказчика, не «код станет чище»
ADM-3  before.value и after.value заполнены, before.method == after.method
ADM-4  failing_test.failed_before == true, output_excerpt ≠ ∅
ADM-5  suite_after заполнен; падений не больше, чем в suite_before
ADM-6  migration ≠ null → в rollback описан downgrade и подтверждён бэкап
ADM-7  rollback ≠ ∅
ADM-8  status=PARTIAL → перечислено непокрытое
ADM-9  текст не содержит: «в целом», «улучшено», «оптимизировано»,
       «отрефакторено» без числа рядом
```

# §2. НАСТОЯЩАЯ КРИТИЧЕСКАЯ ЦЕПОЧКА

Это центральный раздел. Ошибка в его понимании обесценивает половину работы.

## 2.1. Тиры сами по себе не дают ни одной цены

Ранее в проекте фигурировала оценка «заполнить уровни брендов → 24 улики
станут 1513». **Она неверна.** Цепочка длиннее:

```
уровни брендов заполнены
    ↓
уровень кандидата определён            (снимается TIER_UNKNOWN)
    ↓
≥ min_pairs пар (цена KEMP, цена тира X) в одной CELL
    ↓
коэффициент премии подогнан и прошёл валидацию
    ↓
кандидат становится EVIDENCE
```

Без валидированного коэффициента кандидат другого тира остаётся
`REFERENCE_ONLY` с причиной `PREMIUM_NOT_CALIBRATED`
(`backend/src/metis/pricing/candidate_selection.py:1039`). Это не недоделка,
а защита: прямое сравнение цен разных уровней — ровно та ошибка, из-за которой
бюджетный аналог рекомендовали бы поднять до цены оригинала.

Единственное исключение — `SAME_TIER_IDENTITY` (`candidate_selection.py:1030`):
кандидат тира `kemp` проходит без калибровки с коэффициентом 1.

Следствие: **1513 — это потолок гейта тиров, а не число будущих улик.**
Реальное число после заполнения тиров определяется тем, сколько CELL удастся
откалибровать.

# §3. МАТЕМАТИКА УЛУЧШЕНИЯ

Каждая численная оценка в отчёте либо вычислена по формуле отсюда, либо
сопровождается собственной выведенной формулой. «Экспертная оценка» без
формулы — нарушение C-02.

## 3.1. Базовая линия и парное сравнение

Улучшение существует только как пара измерений одной методикой.

```
DELTA(m) = m_after − m_before,  method(m_after) ≡ method(m_before)
```

Запрещено сравнивать:
- число из базы, снятое в разные моменты, без снимка (C-09);
- p95 «до» на 5 прогонах с p95 «после» на 50;
- метрику до изменения объёма данных с метрикой после (каталог вырос с 0 до
  4647 позиций 29 июля — все замеры производительности до этой даты
  несопоставимы с текущими).

## 3.2. Доказательство исправления: мутационная проверка своего фикса

Тест, падающий до правки (C-03), доказывает, что дефект был. Он не
доказывает, что тест поймает **возврат** дефекта другим путём. Для
изменений, влияющих на цену, изоляцию арендаторов и fail-closed границы,
обязательна мутационная проверка собственного фикса:

```
для каждого CHANGE с layer ∈ {domain, data, integration}:
    1. внести в свой же фикс минимальную мутацию, отменяющую его смысл
       (граница <→<=, Decimal→float, снять фильтр, инвертировать условие,
        удалить order_by, вернуть None вместо raise)
    2. прогнать полный набор
    3. мутант обязан быть убит; выживший мутант = тест недостаточен
    4. откатить мутацию, подтвердить чистоту дерева
```

## 3.3. Достаточность выборки для заявления об улучшении

Для доли (например, доля позиций с обоснованной ценой):

```
n₀ = z²·p(1−p)/e²,  z = 1.96
n  = n₀ / (1 + (n₀−1)/N)     поправка на конечную популяцию
```

| `e` | `n₀` | при N = 4647 |
|---:|---:|---:|
| 0.15 | 43 | 43 |
| 0.10 | 97 | 95 |
| 0.05 | 385 | 355 |
| 0.03 | 1068 | 868 |

Интервал Уилсона обязателен вместо нормального: при `k = 0` нормальный
интервал вырождается в `[0,0]` и создаёт ложную уверенность.

```
             p̂ + z²/(2n)          z        ┌──────────────────────┐
center =  ───────────────── ,  ─────── · │ p̂(1−p̂)/n + z²/(4n²) │
            1 + z²/n              1+z²/n   └──────────────────────┘
```

Нулевой результат формулируется через границу: не «дефектов нет», а «в
выборке n = 100 дефектов не найдено, верхняя 95 %-граница доли = 3.7 %».

| `n` | верхняя граница при 0 находок | правило трёх `3/n` |
|---:|---:|---:|
| 30 | 0.114 | 0.100 |
| 50 | 0.071 | 0.060 |
| 100 | 0.037 | 0.030 |
| 385 | 0.010 | 0.008 |

## 3.4. Планирование прогона discovery: yield и требуемый объём

Пилот измеряет yield, дальше объём считается, а не угадывается.

```
YIELD_cell(c, t) = пар в CELL (c,t) / позиций каталога категории c,
                   прогнанных через discovery

требуемое число позиций категории c для калибровки CELL (c,t):
    N_req(c,t) = ⌈ min_pairs / YIELD_cell(c,t) ⌉

требуемое время прогона (закон Литтла):
    T = N · R · S / C
        N — позиций, R — запросов на позицию, S — пауза rate-limit,
        C — параллельность
```

Измерено на пилоте 37 позиций: 349 запросов, то есть `R ≈ 9.4`.
Пример подстановки при `S = 2.5 с`, `C = 2`, `N = 400`:

```
T = 400 · 9.4 · 2.5 / 2 = 4700 с ≈ 78 мин
```

Числа `R`, `S`, `C` заменить измеренными на своём пилоте.

**Порог доверия yield.** Если в CELL после прогона `n` позиций получено `k`
пар, экстраполировать `N_req` допустимо только при `k ≥ 5`; при `k < 5`
писать «yield не измерен», а не делить на почти ноль.

## 3.5. Качество подбора: precision, recall, асимметрия стоимости

**Это измерение никогда не делалось.** Без него неизвестно, сколько из 24
улик — настоящие сопоставимые товары. Прецедент, показывающий цену незнания:
15 из 39 улик были шнеками для мясорубок, и обнаружено это только вручную.

```
              предсказано:  сопоставимо   не сопоставимо
факт сопоставимо                TP              FN
факт не сопоставимо             FP              TN

precision = TP/(TP+FP)     recall = TP/(TP+FN)
Fᵦ = (1+β²)·P·R / (β²·P + R)
```

Асимметрия: ложное совпадение (FP) даёт цену по чужому товару — прямой
денежный ущерб; ложный пропуск (FN) — упущенная выгода. При
`λ = C_FP / C_FN`:

```
оптимальный порог t* = argmin_t [ λ·FP(t) + FN(t) ]
```

Для ценообразования `λ > 1`, следовательно `β < 1`: точность важнее полноты.
**Значение `λ` агент не назначает** (C-10): строит кривую
`(t, precision, recall, λ·FP+FN)` для `λ ∈ {1, 3, 10}` и передаёт выбор
владельцу.

**Размер золотого набора.** Для precision с предельной ошибкой `e = 0.10` при
95 % нужно ≥ 97 размеченных пар (§3.3). Меньший набор допустим, но интервал
Уилсона указывается рядом с числом обязательно.

## 3.6. Производительность: как сравнить честно

```
ЗАПРЕЩЕНО: среднее время ответа.
ОБЯЗАТЕЛЬНО: p50, p95, p99, max, n прогонов, объём БД на момент замера.
```

Минимум `n = 30` на эндпоинт. При `n = 30` p95 — это второе худшее значение,
и это указывается прямо.

Сравнение «до/после» двух точечных p95 некорректно: p95 сам является оценкой с
разбросом. Требуется одно из двух:

```
(а) бутстрэп: 1000 ресэмплов каждой серии, доверительный интервал разности
    p95; улучшение заявляется, только если интервал не содержит нуля;
(б) непараметрический тест на сдвиг распределения (Манна—Уитни) с указанием
    p-value и размера эффекта.
```

Модель стоимости последовательного сканирования, измеренная на этом проекте:

```
поиск по нормализованному коду на listings без индекса по выражению:
    0.6 с при N = 49 275 строк  →  c = 12.18 мкс/строка
T_scan(N) = c · N   (линейно, план Seq Scan)
```

| `N` | `T_scan` |
|---:|---:|
| 49 275 | 0.60 с |
| 200 000 | 2.44 с |
| 1 000 000 | 12.18 с |

Индекс по выражению переводит в `O(log N + k)`. Требование: назвать `N*`, при
котором нарушается целевой SLO, а не писать «может тормозить».

Числа — условные единицы трудоёмкости для расчёта. Агент заменяет своими и
**пересчитывает** критический путь.

```
Σ работ         = 2+2+6+6+5+6+4+6+5+4+5+4+4+8+3 = 70
критический путь = WP-0(2) → WP-1(2) → WP-2(6) → WP-3(6) → WP-15(3) = 19
минимум исполнителей = ⌈70/19⌉ = 4
```

Смысл: цепочка `discovery → золотой набор → приёмка` длиннее любого
одиночного пакета, поэтому прогон запускается первым и идёт в фоне, пока
делается остальное.

**Стоп-условия, нарушение которых запрещает движение дальше:**


## 11.3. Валидатор журнала — прогонять перед сдачей

Сохранить как `.artifacts/<stage>/tools/validate_changes.py`, запускать

```python
#!/usr/bin/env python3
"""Проверяет CHANGES.jsonl по правилам ADM-1..ADM-9 мастер-промпта улучшения."""
from __future__ import annotations

import json
import pathlib
import re
import sys

BANNED = ("в целом", "улучшено", "оптимизировано", "отрефакторено")
NUMBER = re.compile(r"\d")


def _suite_failures(text: str) -> int:
    """Число падений из строки вида '1483 passed, 7 skipped' / '100 passed, 10 failed'."""
    match = re.search(r"(\d+)\s+failed", text)
    return int(match.group(1)) if match else 0


def check(rec: dict, root: pathlib.Path) -> list[str]:
    errs: list[str] = []

    if not rec.get("files"):
        errs.append("ADM-1: files пуст")
    for path in rec.get("files", []):
        if not (root / path).exists():
            errs.append(f"ADM-1: файла нет на диске: {path}")

    why = str(rec.get("why", ""))
    if len(why) < 20:
        errs.append("ADM-2: why слишком короткое, нужна причина в единицах заказчика")

    before, after = rec.get("before") or {}, rec.get("after") or {}
    for name, block in (("before", before), ("after", after)):
        if block.get("value") is None:
            errs.append(f"ADM-3: {name}.value не заполнен")
        if not str(block.get("method", "")).strip():
            errs.append(f"ADM-3: {name}.method не заполнен")
    if before.get("method") and before.get("method") != after.get("method"):
        errs.append("ADM-3: методика before и after различается — сравнение невалидно")

    test = rec.get("failing_test") or {}
    if test.get("failed_before") is not True:
        errs.append("ADM-4: failing_test.failed_before должно быть true")
    if len(str(test.get("output_excerpt", ""))) < 10:
        errs.append("ADM-4: нет вывода падения на прежнем коде")

    sb, sa = rec.get("suite_before") or {}, rec.get("suite_after") or {}
    for side, block in (("suite_before", sb), ("suite_after", sa)):
        for key in ("backend", "frontend"):
            if not str(block.get(key, "")).strip():
                errs.append(f"ADM-5: {side}.{key} не заполнен")
    for key in ("backend", "frontend"):
        if sb.get(key) and sa.get(key):
            if _suite_failures(str(sa[key])) > _suite_failures(str(sb[key])):
                errs.append(f"ADM-5: падений в {key} стало больше, чем было")

    if rec.get("migration") and "downgrade" not in str(rec.get("rollback", "")).lower():
        errs.append("ADM-6: миграция без описанного downgrade в rollback")

    if not str(rec.get("rollback", "")).strip():
        errs.append("ADM-7: rollback пуст")

    if rec.get("status") == "PARTIAL" and "непокрыт" not in json.dumps(
        rec, ensure_ascii=False
    ).lower():
        errs.append("ADM-8: status=PARTIAL без перечня непокрытого")

    blob = " ".join(str(rec.get(field, "")) for field in ("title", "why", "risk")).lower()
    for word in BANNED:
        index = blob.find(word)
        if index >= 0 and not NUMBER.search(blob[index : index + 80]):
            errs.append(f"ADM-9: «{word}» без числа рядом")

    return errs


def main(argv: list[str]) -> int:
    if len(argv) != 2:
        print("usage: validate_changes.py CHANGES.jsonl", file=sys.stderr)
        return 2
    path = pathlib.Path(argv[1]).resolve()
    # корень репозитория: .artifacts/<stage>/tools/ → на три уровня выше
    root = path.parent
    for _ in range(4):
        if (root / "backend").is_dir():
            break
        root = root.parent

    failures = 0
    records: list[dict] = []
    for lineno, raw in enumerate(path.read_text(encoding="utf-8").splitlines(), 1):
        if not raw.strip():
            continue
        try:
            rec = json.loads(raw)
        except json.JSONDecodeError as exc:
            print(f"line {lineno}: невалидный JSON: {exc}")
            failures += 1
            continue
        records.append(rec)
        for err in check(rec, root):
            print(f"{rec.get('id', f'line {lineno}')}: {err}")
            failures += 1

    ids = [rec.get("id") for rec in records]
    if len(ids) != len(set(ids)):
        print("дублирующиеся id в журнале")
        failures += 1

    done = sum(1 for rec in records if rec.get("status") == "DONE")
    print(f"изменений: {len(records)}; DONE: {done}; корень: {root}")
    print("ОШИБОК: 0" if failures == 0 else f"ОШИБОК: {failures}")
    return 1 if failures else 0
```
