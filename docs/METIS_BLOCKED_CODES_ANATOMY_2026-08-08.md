# Из чего состоят 1974 кода без подтверждённого OE — 2026-08-08

Всё это время «позиции без OE» были одним числом. Оно оказалось двумя разными
задачами, и внешние данные нужны только одной из них.

Расчёт файловый (`plan_identity` по двум справочникам и `kemp_site_numbers.csv`,
`part_numbers_raw=()`), поэтому население — 7193 кода справочников, а не 4663
строки каталога в базе. Для базы числа будут меньше: собственный экспорт даёт
части строк номера, которых у файлового расчёта нет.

## Разделение

| | кодов |
|---|---:|
| заблокировано всего | 1974 |
| **утверждения OE нет ни от одного источника** | **1510** |
| **OE утверждён справочником заказчика, но граф в карантине** | **464** |

Правило, которое их разделяет, — `_asserted_numbers`
(`catalog_identity_reparse.py:1222`):

```python
if (
    graph.canonical
    and not graph.anomalies
    and assertion_is_eligible(graph.canonical_sources, evidence_confirmed=True)
):
```

Для всех 464 третье условие выполняется: якорь назван
`KEMP_REFERENCE_MAP_V2`/`V1` — оба `status: CONFIRMED`, оба `asserts_oe: true`.
Держит их второе условие.

### 1510 — здесь и только здесь нужен внешний источник

Номера у этих кодов есть, но все пришли из колонок, которые не утверждают, что
номер оригинальный: артикул поставщика, собственный код экспорта, карточка
kemp.ua (`REVIEW`). Статус — `ONLY_CROSS_LIST_NUMBERS`.

Это ровно та работа, для которой строился приём avto.pro: секция
`#original-manufacturers` — единственный доступный нам источник, который
утверждает «это номер автопроизводителя», а не «это ещё один номер той же
детали».

| **якорь чистый, карантин пришёл с соседнего ребра** | **338** |

Пример из вторых: код `7764566`, якорь `4A0823359B` — OE Audi, назван
справочником, ни с кем не делится. В графе есть второе ребро — на `27677`,
артикул поставщика, который принадлежит нескольким внутренним кодам. Аномалия
`SHARED_ARTICLE_FANOUT` ставится на **граф целиком**
(`identity_graph.py:633`), и `not graph.anomalies` гасит вместе с ребром и
чистый якорь.

Ещё примеры той же формы: `7764947` → `4A0959101A` при ребре `0130111162`;
`7764997` → `026121144A` при ребре `026121145E`; `77644727` → `6Q0959455AF`
при ребре `443121321`.

Первые 126 — настоящая неоднозначность: один номер действительно принадлежит
двум деталям, и без различающего признака (сторона, комплектность) выбрать
нельзя. Это работа для семантики, а не для нового источника номеров.

Все 464 выгружены в `quarantined_oe_review.csv` — код, якорь, источники якоря,
аномалия, размножен ли сам якорь, соседние номера, название. Разговор о ширине
гейта без этого списка беспредметен.

**Осознанная ли это широта, решать не мне.** Комментария у условия
`not graph.anomalies` нет, отдельного теста на него тоже нет: единственный
близкий — `test_canonical_only_public_fanout_cannot_confirm_or_fill_oe` — про
случай, когда сам якорь и есть размножившийся номер, то есть про те 126, а не
про 338. Сужение гейта до «аномалия на самом якоре» — изменение правила доверия,
и оно требует решения заказчика, а не правки на месте.

## Почему разбирать prom вручную не нужно

Репозиторий уже читает prom.ua структурно. `Product` собирает `part_numbers`
из блока характеристик через `_extract_labelled_part_numbers`
(`services/parser_models.py:327`) по подписям `Артикул`/`Код запчастини`, есть
отдельный `extract_labelled_original_oe_numbers` для подписей OE/OEM, а
`CatalogItem.part_numbers_raw` прямо описан как «Identity read out of the Prom
characteristics block». `catalog_import.py:476` ходит через тот же
`PromGateway`.

То есть store-sync четырёх витрин — не новый парсинг, а операционный прогон,
который берёт из карточки поле, а не текст страницы. Требует postgres.

Оговорка: `PromGateway.scrape` (`gateway.py:484`) отдаёт товары со страниц
листинга и не вызывает слияние с детальной карточкой — им пользуется
`search_enriched`. Насколько полон блок характеристик в листинге, проверяется
только живым прогоном.

## Главное: подпись OE нужна для чужих карточек, и там её не читали

Сторона офферов имеет **собственный** набор подписей, никак не связанный с
`_ORIGINAL_OE_ATTRIBUTE_LABELS`: `_oe_label_confidence`
(`services/offer_identity.py:1758`). И `extract_oe_evidence` устроен так, что
непризнанная подпись не понижается в весе, а выбрасывает характеристику целиком:

```python
label_confidence = _oe_label_confidence(label)
if label_confidence is None:
    continue
```

Что этот набор признавал до 2026-08-08 (замер прямым вызовом):

| подпись | было |
|---|---|
| `OE`, `OEM`, `OEM NO` | 0.97 |
| `OE номер` (латинские O, E) | 0.97 |
| `Крос-номери`, `Кросс-номера`, `Крос-код` | 0.97 |
| `Артикул`, `Код запчастини`, `Код виробника` | 0.88 |
| **`Оригінальні номери`** | **не признана** |
| **`Оригинальные номера`** | **не признана** |
| **`Оригінальний номер` / `Оригинальный номер`** | **не признана** |
| **`Номер оригіналу` / `Номера оригинала`** | **не признана** |
| **`ОЕ номер` (кириллические О, Е)** | **не признана** |
| **`OEM номери`** | **не признана** |

`OEНОМЕР` в наборе записан латинскими `O` и `E` (кодпоинты `0x4f 0x45`), поэтому
кириллическое «ОЕ» ему никогда не равнялось — а именно так подписана карточка
kemp.ua в фикстуре репозитория.

**Цена этого.** На карточке конкурента, где номера стоят под «Оригінальні
номери», из самого сильного поля не извлекалась **ни одна** улика. Оффер
приходилось проверять по `mpn`, `oe_raw` и заголовку — а `oe_raw` пуст у всех
1035 товаров сохранённого живого корпуса.

**Насколько это распространено.** Выгрузка витрин от 2026-08-08: блок
«Оригінальні номери» стоит на **1316 карточках из 1316**, 11916 номеров.

Починено тестом-первым (`tests/test_offer_identity.py`): 9 написаний + проверка,
что «Оригінальні номери» остаётся `LABELED_CHARACTERISTIC`, а не
`COMPATIBLE_REFERENCE_LIST` (последний живёт за границей подтверждённого кросса,
а список оригинальных номеров называет саму деталь), + негативные случаи «Не
оригінальний номер», «Оригінальний номер аналога», «Замінник оригіналу» —
сравнение осталось точным, а не подстрочным. Тариф тот же, что у `OE`: написание
не есть уровень доверия.

`OE_EXTRACTOR_VERSION` поднят `v5` → `v6`: `oe_reenrichment` метёт по
`oe_extractor_version != OE_EXTRACTOR_VERSION` (`oe_reenrichment.py:539`), иначе
каждое уже сохранённое наблюдение осталось бы с вердиктом, вынесенным когда поле
было невидимым.

## Магазин заказчика утверждает OE, и мы его не слышим

Присланные файлы сняты с собственных витрин заказчика. Это не сторонний
агрегатор, чью независимость надо доказывать: продавец говорит про свой товар,
но это всё равно не превращает page-area выгрузку в автоматически подтверждённый
OE. Для pricing identity источник разделён на два слоя: структурированное
поле exact detail-card (`OWN_STORE_LABELLED_OE`, `REVIEW`) и производный
page-area candidate export (`OWN_STORE_CANDIDATE_REVIEW`, `asserts_oe: false`).
Оба слоя сохраняются оператору, но ни один не понижает уже подтверждённую
reference-идентичность и не двигает цену без отдельного решения.

**Читать умеем.** `extract_labelled_original_oe_numbers`
(`services/parser_models.py:358`) отдельно от общего блока артикулов достаёт
значения характеристик с подписью OE/OEM/«оригінальний номер». Комментарий там
прямо говорит: только явная подпись оригинального номера может перебить
поставщицкий MPN, а общий «Артикул» — не может.

**В identity graph источник есть, но он review-only.** Для точного owner-card
поля сохраняются URL, product id, внутренний код, label, raw/normalized value,
brand, title/spec, parser/source version, file/response SHA и timestamp.
`OWN_STORE_LABELLED_OE` не смешивается с `OWN_EXPORT_CHARACTERISTIC` или
`OWN_EXPORT_CODE`; последние остаются non-OE cross/code источниками.

**И подписи не совпадали.** Набор `_ORIGINAL_OE_ATTRIBUTE_LABELS` сравнивал
точной строкой и содержал только голые формы единственного числа. Мимо шли:

| подпись | где встречается |
|---|---|
| `Оригінальні номери` | витрина заказчика на prom, 87 карточек из 1317 |
| `Оригинальные номера` | та же подпись по-русски |
| `ОЕ номер` (кириллические О и Е) | карточка kemp.ua, дословно в `test_kemp_site_harvest.CARD` |
| `OE номер`, `OEM номери` | смешанное написание там же |

Кириллическое «ОЕ» никогда не равно латинскому `oe`, а множественное число не
равно единственному. Починено тестом-первым (`test_matching.py`, 5 подписей +
негативный случай: «Не оригінальний номер» и «Оригінальний номер аналога»
утверждениями не становятся). Набор остался точным, а не подстрочным, — именно
из-за этих двух.

**Разрыв listing → detail card закрыт в коде fail-closed способом:**
`catalog_import.py` включает `ScrapeConfig(enrich_details=True)`, а
`PromGateway.scrape` запрашивает exact product card и сохраняет
`detail_evidence`. При missing/blocked/mismatched detail card сохраняется
failure/review evidence; title и общий DOM никогда не становятся OEM.

Текущая цепочка:

| звено | состояние |
|---|---|
| импорт витрины забирает блок характеристик | **да**, через exact detail-card enrichment |
| подпись «Оригінальні номери» / «ОЕ номер» распознаётся | **да**, точным label matcher'ом |
| явно подписанный OE становится автоматическим pricing identity | **нет**, только `REVIEW_OWNER_ASSERTED_OE` до независимого подтверждения/ручного решения |

Из этого следует: store-sync теперь собирает raw detail evidence, но его
owner-assertion остаётся отдельной review-очередью. Это сохраняет высокий recall
для ручной приёмки и одновременно не превращает собственную витрину в второй
независимый голос того же заказчика.

## Что из этого следует

1. **Сначала собственная витрина, а не avto.pro.** Порядок был выбран неверно:
   сторонний агрегатор проверялся раньше первоисточника. Витрина заказчика
   печатает списки оригинальных номеров — доказано её же выгрузкой: 135
   заблокированных кодов получают номер, которого нет в справочниках, с 1316
   карточек. Работа здесь наша, а не заказчика: запрос карточки товара в импорте
   витрин, затем источник в `identity_graph.yaml`. Скрейпить руками больше
   ничего не нужно — обход области страницы даёт REVIEW с хвостом текста, а
   запрос карточки даст чистое поле.
2. **1510 кодам** может понадобиться avto.pro — но сколько из них закрывает
   собственная витрина, неизвестно: обход покрыл 1316 карточек, а витрины
   заказчика шире. Приём и драйвер avto.pro готовы и подождут.
3. **338 кодам** не нужно ничего, кроме решения о ширине гейта.
4. **126 кодам** нужен различающий признак, а не номер.
5. Оба присланных файла в `backend/data/` не принимаются: они снимают со
   страниц текст, а нужное поле берётся структурно тем же прогоном.
