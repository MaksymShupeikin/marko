# МАСТЕР-ПРОМПТ: СКВОЗНОЙ ФУНКЦИОНАЛЬНЫЙ АУДИТ UI И БЭКЕНДА MARKO/METIS

**Версия:** 1.0
**Дата:** 2026-07-26
**Тип документа:** исполняемая инструкция для ИИ-агента (аудит + разбор + рекомендации)
**Предмет:** все пользовательские функции проекта — Flutter-клиент `frontend/`
и Python-бэкенд `backend/` — их контракты, состояния, наблюдаемость и
пригодность к продакшену.
**Результат:** реестр находок с доказательствами + приоритизированная
дорожная карта усовершенствования. Не рефакторинг. Не переписывание.

## §0. КОНТРАКТ ИСПОЛНЕНИЯ

### 0.1. Роль и режим

```
ROLE   := инженер-аудитор, который доказывает утверждения кодом и числами,
          а не описывает впечатления от чтения.
MODE   := читать → воспроизводить → измерять → фиксировать находку.
          Каждая находка закрывается либо доказательством (repro), либо
          статусом UNVERIFIED с указанием, чего не хватило.
BIAS   := презумпция «функция сломана или неполна, пока не показан проход
          по её happy-path И по её краевым веткам». Зелёный тест не есть
          доказательство: тест мог проверять не то.
OUTPUT := машиночитаемый реестр находок (§0.4) + человекочитаемый отчёт (§6).
```

### 0.2. Жёсткие ограничения — читать буквально

```
CONSTRAINT_1 (НЕ ДУМАЙ О ТОКЕНАХ, ОБЪЁМЕ И ВРЕМЕНИ)
    Бюджет чтения, вывода, числа прогонов и итераций НЕ ОГРАНИЧЕН.
    Файл читается целиком, а не «первые 200 строк». Если в модуле 40
    сервисов — просматриваются все 40, а не «ключевые». Запрещены
    формулировки: «для краткости», «аналогично для остальных»,
    «и так далее», «опустим», «предположительно так же».
    Если чего-то не читал — писать UNREAD, а не додумывать.

CONSTRAINT_2 (НЕ УПРОЩАЙ ЗАДАЧУ)
    Запрещены подмены:
      полный обход      → выборка «репрезентативных» файлов
      чтение тела       → чтение имени функции и докстринга
      запуск            → рассуждение о том, что было бы при запуске
      проверка ассертов → доверие к названию теста
      65 эндпоинтов     → «основные эндпоинты»
    Если WP говорит «все экраны» — значит все 6 фич-модулей UI, а не 2.

CONSTRAINT_3 (НИКАКИХ ЗАГЛУШЕК В РЕЗУЛЬТАТЕ)
    Запрещены находки вида «возможно, стоит улучшить обработку ошибок».
    Находка обязана содержать: файл, строку, конкретный вход, конкретный
    наблюдаемый выход, конкретный ожидаемый выход.

CONSTRAINT_4 (FAIL-CLOSED ПРИ НЕУВЕРЕННОСТИ)
    Не уверен в числе → вычисли. Не можешь вычислить → BLOCKED с указанием,
    что именно блокирует. Правдоподобное число вместо измеренного —
    худшая из возможных ошибок этого документа.

CONSTRAINT_5 (ОБЯЗАТЕЛЬНАЯ ВАРИАЦИЯ)
    Ни один WP не закрывается после одного успешного прохода. До закрытия
    обязателен прогон матрицы вариаций §4, относящейся к этому WP.
    Вариация, вскрывшая расхождение, превращается в находку, а WP
    остаётся открытым, пока находка не зафиксирована.

CONSTRAINT_6 (НЕ ЧИНИТЬ ПО ХОДУ АУДИТА)
    Это аудит. Правки кода запрещены, КРОМЕ:
      (a) создания новых тестов, доказывающих находку (в отдельном файле
          `backend/tests/test_audit_findings.py` / `frontend/test/audit_findings_test.dart`);
      (b) временных диагностических скриптов в `.artifacts/<stage>/`.
    Правка продакшн-кода — отдельный этап после приёмки реестра владельцем.
    Причина: смешение аудита и починки делает невозможным измерение «до».

CONSTRAINT_7 (НЕ ЗАПУСКАТЬ РЕПОЗИТОРНЫЕ ФОРМАТТЕРЫ ШИРОКО)
    ЗАПРЕЩЕНО: `ruff format src tests`, `dart format .`, любой массовый
    автофикс. Это создаёт сотни несвязанных изменений и делает диff
    аудита нечитаемым. Разрешено только на файлах, созданных самим
    агентом, поимённо.

CONSTRAINT_8 (СРЕДА ИЗМЕНЧИВА — ФИКСИРУЙ СНИМОК)
    В проекте работают фоновые сервисы (`scheduler`, `worker`,
    `pricing-worker`, `store-sync-worker`), которые пишут в БД во время
    аудита. Любая метрика из БД обязана сопровождаться снимком:
    `(таблица, COUNT(*), MAX(created_at), timestamp измерения)`.
    Два числа, снятые в разные моменты, сравнивать запрещено.

CONSTRAINT_9 (КОНТРАКТ REASON-КОДОВ НЕПРИКОСНОВЕНЕН)
    Идентификаторы, имена гейтов, reason codes (`OWN_SELLER`,
    `TIER_UNKNOWN`, `CATEGORY_NOT_AUTOPARTS`, …), ключи конфига —
    английские и являются контрактом между Python, PostgreSQL
    (`CandidateVerdict.reason`, `catalog_discovery_offers.selection_reason`)
    и бейджами Flutter. Предлагать их переименование можно только как
    находку с оценкой стоимости миграции всех трёх слоёв.

CONSTRAINT_10 (ЯЗЫК)
    Отчёты, находки, комментарии — русский. Идентификаторы, коды, пути,
    команды — как в коде. Двуязычные reason-коды не вводить.

CONSTRAINT_11 (ДЕФЕКТ СРЕДЫ ЗАФИКСИРОВАН, НЕ ОТКРЫВАТЬ ЗАНОВО)
    Каталог проекта содержит неразрывный пробел U+00A0 в имени
    (`marko — копия`). Из-за этого падают: `flutter analyze`
    (FormatException в LSP-канале) и прямое чтение путей рядом
    инструментов. Обход: работать через ASCII-симлинк или ASCII-копию.
    Это известный дефект окружения, НЕ находка аудита, в реестр не вносить.

CONSTRAINT_12 (КОНФЛИКТ РЕГЛАМЕНТОВ — СПРОСИТЬ, НЕ ВЫБИРАТЬ)
    `AGENTS.md` требует governance-футер Section 15.1 + Section 16 в каждом
    ответе. `METIS MASTER PLAN.md` (мета-правило 9) этот слой прямо
    запрещает как бесполезный. Агент НЕ выбирает сам: спрашивает владельца
    один раз в начале и фиксирует ответ в шапке отчёта.
```

### 0.3. Обозначения

```
F        := функция системы — наблюдаемая пользователем или внешним
            вызывающим единица поведения (эндпоинт, экран, действие на
            экране, фоновая задача).
F_ui     := множество функций UI (экраны, диалоги, действия)
F_api    := множество функций API (эндпоинты)
F_job    := множество фоновых функций (Celery-задачи, планировщик)
S(F)     := множество наблюдаемых состояний F
           ⊇ {loading, empty, partial, error, forbidden, success}
C(F)     := контракт F: (вход, предусловия, выход, инварианты, побочные эффекты)
E(F)     := множество путей отказа F
O(F)     := наблюдаемость F: что попадает в логи/метрики/БД при каждом исходе
T(F)     := тесты, покрывающие F
FINDING  := единица результата аудита (§0.4)
severity := BLOCKER | CRITICAL | MAJOR | MINOR | INFO
confidence := PROVEN | LIKELY | UNVERIFIED
```

### 0.4. FINDING — единица результата (машиночитаемая схема)

Каждая находка записывается объектом. Файл реестра:
`.artifacts/<stage>/FINDINGS.jsonl`, по одному JSON-объекту на строку.

```json
{
  "id": "F-0001",
  "wp": "WP-5",
  "layer": "ui | api | domain | data | integration | infra | test",
  "feature": "catalog.discovery_button",
  "title": "одна строка, глагольная формулировка дефекта",
  "severity": "BLOCKER|CRITICAL|MAJOR|MINOR|INFO",
  "confidence": "PROVEN|LIKELY|UNVERIFIED",
  "location": [{"path": "backend/src/...", "line": 123}],
  "observed": "что происходит фактически",
  "expected": "что должно происходить и на каком основании",
  "basis": "код | спецификация | измерение | требование заказчика",
  "repro": {
    "kind": "test|command|sql|ui_steps",
    "steps": ["точные шаги/команды"],
    "evidence_path": ".artifacts/<stage>/evidence/F-0001.txt"
  },
  "impact": {
    "who": "заказчик|оператор|разработчик",
    "scenario": "конкретный сценарий, где это вредит",
    "measured": "число, если измеримо, иначе null"
  },
  "fix_sketch": "минимальное изменение, закрывающее находку",
  "fix_cost": "S|M|L",
  "risk_if_fixed": "что может сломаться от исправления",
  "depends_on": ["F-0002"],
  "status": "OPEN|BLOCKED|WONTFIX_PROPOSED"
}
```

**Правило допустимости:** находка с `confidence: PROVEN` обязана иметь
непустой `repro` с воспроизводимым артефактом. Находка без `repro`
не может иметь severity выше `MINOR`.

### 0.5. Формат закрытия пакета работ

```
WP-<N> <название>
Область:            <что именно обойдено, с числом единиц>
Обойдено:           <X из Y> (100% обязательно, иначе WP не закрыт)
Находок:            BLOCKER <a> · CRITICAL <b> · MAJOR <c> · MINOR <d> · INFO <e>
Из них PROVEN:      <n>
Метрика WP:         <числовой показатель, определённый в самом WP>
Вариации §4:        <перечень прогнанных, с результатом каждой>
Команды:            <точные команды воспроизведения>
Артефакты:          <пути>
Незакрытое:         <что осталось UNVERIFIED и почему>
```


## §2. ФОРМАЛЬНАЯ МОДЕЛЬ АУДИТА

### 2.1. Функция как наблюдаемая тройка

Каждая функция описывается тройкой `F = (C, S, O)`:

```
C(F) = (I, P, Ω, Inv, Eff)
    I   — область входа
    P   — предусловия (что обязано быть истинно до вызова)
    Ω   — область выхода
    Inv — инварианты, сохраняемые вызовом
    Eff — побочные эффекты (запись в БД, внешний запрос, файл)

S(F) ⊇ {loading, empty, partial, error, forbidden, success}
O(F) : S(F) → Evidence   (что наблюдаемо снаружи в каждом состоянии)
```

**Функция считается полной**, если:

```
COMPLETE(F) ⟺ ∀s ∈ S(F) : O(F)(s) ≠ ∅
              ∧ ∀e ∈ E(F) : ∃ обработчик, дающий определённое состояние
              ∧ Inv сохраняются на всех путях, включая пути отказа
```

Аудит ищет нарушения `COMPLETE(F)`. Типовые нарушения:

| Нарушение | Признак в коде |
|---|---|
| `S` неполно | UI не имеет ветки `empty` или `error` |
| `O` пусто | отказ проглочен `except: pass` / `catch {}` |
| `Inv` нарушен | частичная запись без транзакции/отката |
| `E` не покрыт | внешний вызов без обработки таймаута |
| `P` не проверено | эндпоинт не валидирует принадлежность workspace |

### 2.2. Классификация находки

```
severity := f(последствие, обратимость, охват)

BLOCKER  — приводит к неверному коммерческому решению (неправильная цена),
           к утечке данных между workspace, к потере данных.
CRITICAL — функция недоступна или молча даёт неверный результат в
           штатном сценарии.
MAJOR    — функция работает, но нарушает контракт в краевом сценарии,
           либо отказ ненаблюдаем (нельзя диагностировать в проде).
MINOR    — неудобство, косметика, дублирование, отсутствие теста на
           существующее корректное поведение.
INFO     — наблюдение без дефекта; кандидат в улучшения.
```

Правило эскалации: **любая находка, влияющая на цену, — минимум CRITICAL.**
Обоснование: неверный tier/премия/медиана не падает с исключением, а молча
портит каждую рекомендацию ниже по конвейеру.

### 2.3. Критерий допустимости находки

```
ADMISSIBLE(finding) ⟺
      finding.location ≠ ∅
    ∧ finding.observed ≠ ∅ ∧ finding.expected ≠ ∅
    ∧ finding.basis ∈ {код, спецификация, измерение, требование}
    ∧ (finding.confidence = PROVEN → finding.repro.evidence_path существует)
    ∧ ¬ содержит слов: «возможно», «желательно», «стоит подумать»
```

Недопустимая находка не попадает в реестр. Вместо неё — либо доказательство,
либо запись в `OPEN_QUESTIONS.md` с формулировкой вопроса.

### 2.4. Приоритизация

```
priority(f) = w_sev(f.severity) · w_conf(f.confidence) / w_cost(f.fix_cost)

w_sev  : BLOCKER=100, CRITICAL=40, MAJOR=10, MINOR=2, INFO=0.5
w_conf : PROVEN=1.0, LIKELY=0.6, UNVERIFIED=0.25
w_cost : S=1, M=3, L=8
```

Сортировка реестра — по убыванию `priority`. Формула фиксирована;
менять веса можно только явным решением владельца, с записью в отчёте.

### 2.5. Метрики аудита (считаются на каждом стоп-гейте)

```
coverage_api   = |обойдённые эндпоинты| / 65
coverage_ui    = |обойдённые экраны+диалоги| / |всего|
state_coverage = Σ_F |реализованные s ∈ S(F)| / Σ_F |требуемые s ∈ S(F)|
silent_failure_count = |точек, где отказ не наблюдаем|
contract_drift_count = |расхождений между схемой API и моделью UI|
proven_ratio   = |findings PROVEN| / |findings|
```

## §3. ПАКЕТЫ РАБОТ

### WP-0. Инвентаризация и карта системы

**Цель:** получить полный список функций, чтобы последующие WP имели
знаменатель. Без этого `coverage_*` невычислим.

**Шаги:**
1. Построить таблицу `F_api`: для каждого из 65 эндпоинтов —
   `метод, путь, роутер, зависимости (Depends), схема запроса, схема
   ответа, кто вызывает из UI`.
   Вызывающего искать в `frontend/lib/features/*/[feature]_api.dart`
   и `frontend/lib/core/api_client.dart`.
2. Построить таблицу `F_ui`: для каждого экрана и диалога —
   `путь роута (app_router.dart), контроллер, какие API дёргает,
   какие состояния отрисовывает`.
3. Построить таблицу `F_job`: Celery-задачи и расписание
   (`backend/src/marko/worker/`, `beat_singleton.py`).
4. Отметить **сироты**: эндпоинты, не вызываемые ни одним UI-файлом;
   экраны, не достижимые из навигации; сервисы, не импортируемые нигде.
5. Отметить **дубли**: две функции с пересекающейся ответственностью.

**Артефакт:** `.artifacts/<stage>/INVENTORY.json` с тремя таблицами.

**Метрика WP:** `|F_api| + |F_ui| + |F_job|`, число сирот, число дублей.

**Стоп-гейт:** таблица с числами; 100% эндпоинтов классифицированы как
«используется UI / используется извне / сирота».

### WP-1. Контракт API ↔ UI

**Цель:** найти расхождения между тем, что бэкенд отдаёт, и тем, что
клиент ожидает. Это класс дефектов, который не ловится ни backend-тестами,
ни widget-тестами по отдельности.

**Шаги:**
1. Для каждого эндпоинта взять Pydantic-схему ответа
   (`backend/src/marko/api/schemas/`) и соответствующую Dart-модель
   (`frontend/lib/features/*/[feature]_models.dart`).
2. Сверить поле в поле: имя, тип, nullable, значение по умолчанию.
3. Проверить обработку в Dart: `json['x'] as String` на nullable-поле —

| 8 | `None`/пустая строка в идентификаторе | `norm_oem(None)` не падает | 2 |
| 9 | идентификатор с ведущими нулями | соответствие спецификации §2.1 | 2 |
| 10 | смешение кириллицы и латиницы, гомоглифы | нормализация текста и брендов | 2 |

| 12 | HTTP 3xx на странице > 1 | конец пагинации, собранное сохраняется | 4 |
| 13 | HTTP 403/429/500 | не глотается, попадает в трассу | 4 |

| 17 | пустой список от API | ветка `empty`, не бесконечный спиннер | 6 |
| 18 | ошибка сети в UI | ветка `error` с действием | 6 |

| 20 | частичные данные | видно, что данные неполны | 6 |

**Правило:** результат каждой вариации фиксируется как
`(вариация, ожидание, факт, совпало/нет)`. Формулировка «проверено,
работает» без указания факта — нарушение CONSTRAINT_3.


Отчёт считается закрытым, только когда все десять пунктов заполнены
числами. Формулировки «выполнено», «успешно», «в целом хорошо» без цифр —
нарушение CONSTRAINT_3.

## §7. АНТИПАТТЕРНЫ — запрещённые формы результата

```
ЗАПРЕЩЕНО:
  «код в целом хорошего качества»            → нет числа, нет находки
  «рекомендуется улучшить обработку ошибок»  → нет location, нет repro
  «покрытие тестами достаточное»             → 1154 теста ≠ качество
  «остальные эндпоинты аналогичны»           → нарушение CONSTRAINT_2
  «предположительно, здесь N+1»              → измерь или пометь UNVERIFIED
  находка без severity или с severity «на глаз» без критерия §2.2
  правка продакшн-кода «заодно»              → нарушение CONSTRAINT_6
  массовый автоформат                        → нарушение CONSTRAINT_7
  сравнение двух чисел из БД, снятых в разные моменты → CONSTRAINT_8
  доменное решение о брендах/тирах, принятое агентом  → §1.3
```
