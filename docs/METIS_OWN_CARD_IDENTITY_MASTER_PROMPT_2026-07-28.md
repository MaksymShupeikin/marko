## 0. КОНТРАКТ ИСПОЛНЕНИЯ

### 0.1. Роль и режим

```
ROLE := инженер, замыкающий разрыв между данными, которые уже лежат в БД
        после импорта Excel, и гейтами, которые эти данные не видят.
MODE := построение + верификация в одном цикле. Каждый пакет работ (WP)
        закрывается числом (метрикой до/после) на реальном экспорте Prom,
        а не описанием намерения.
BIAS := презумпция того, что отказ гейта — следствие отсутствия
        доказательства, а не ошибки логики гейта, пока чтением кода не
        доказано обратное. Гейты fail-closed по замыслу; чинить надо
        поток доказательств, а не порог.
```

### 0.2. Жёсткие ограничения — читать буквально

```

    Ограничений на объём чтения кода, вывода и число прогонов нет.
    Файлы читаются целиком. Формулировки "для краткости", "аналогично
    для остальных", "и т.д." запрещены: если колонок 7 — разбираются 7.

    которого попадает в CrossLink.validation_status, в гейты
    candidate_selection.py, в MarketObservation или в калибровку.
    Обоснование: comparability_policy_hash и calibration_identity_record
```

## 1. ДИАГНОЗ, ОТ КОТОРОГО ОТТАЛКИВАЕМСЯ

Установлено чтением кода 2026-07-28. Эти четыре факта — вход задачи, их не
надо перепроверять с нуля, но каждый обязан быть подтверждён в WP-0 на
реальном файле заказчика.

**Ф-1. Колонка `oe` набивается из «код товару» — это артикул продавца, не OE.**
`_prom_export_mapping` (`xlsx_catalog.py:710`) содержит
`"oe": "код товару"`. Для товара 2141006 «Код товару» = `MG 2141006`
(артикул Metzger). Далее `oe_norm` уходит в `catalog_discovery_query`
(`catalog_discovery.py:179`) и в `_gate_oem_identity`
(`candidate_selection.py:690`) как `expected_oem`. Система по всей цепочке
называет артикул поставщика оригинальным номером.

**Ф-2. Описание товара импортируется, но как источник кроссов не читается.**
`"description": "опис"` присутствует в optional-маппинге
(`xlsx_catalog.py:725`), поле `CatalogItem.description` существует
(`models.py:51`). В нём лежат готовые таблицы «КАТАЛОЖНІ НОМЕРИ АНАЛОГІВ»
(BMW 11121743294, 11121715318, 11127500568, LAND ROVER STC2020, ASHIKA,
SWAG, PROFIT …) и «ЗАСТОСУВАННЯ» (BMW 1/3/5/6/7/8/X3/X5/Z3/Z4/Z8,
Land Rover, MG, Rover). Ни один код к этому полю за кроссами не обращается.

**Ф-3. `CrossLink` строится исключительно из описаний конкурентов.**
`persist_cross_links_for_run` (`cross_links.py:60`) собирает `CrossListing`
из `MarketObservation.description`. Возникает замкнутый круг: гейт требует
подтверждённый кросс → кросс рождается только из наблюдения → наблюдение
рождается только после прохождения гейта.

**Ф-4. Словарь марок неполон, а применимость сравнивается по заголовку.**
`comparability.yaml:113` знает только VW, Toyota, Mercedes, Audi, Skoda,
Seat, BMW. Land Rover, Rover, MG отсутствуют, хотя составляют половину
применимости этого товара. `_gate_applicability`
(`candidate_selection.py:800`) извлекает марки из строки заголовка, тогда
как структурированная применимость лежит в описании неиспользованной.

**Ф-5. Существует справочник KEMP «внутренний номер → реальный артикул», и он не подключён.**
Файл `2_5422575405825567226.xls` (лист `Export`, 4646 строк, колонки
«Наименование | Номер производителя | Фирма изготовитель | Артикул |
фирма по артикулу») даёт для каждого KEMP-номера настоящий артикул и его
бренд: `77641543 → 4B0823359A (VAG)`, `77641702 → 313327 (Sachs)`.
Измерено 2026-07-28 на самом файле:

- `Фирма изготовитель` = `KEMP` во всех 4646 строках — это наш собственный
  ассортимент, а `ProductTier.KEMP` уже первоклассная сущность в коде
  (`is_kemp`, `kemp_reference_count`, `models.py:1886`);
- отображение **строго 1:1**: 4646 уникальных KEMP-номеров, ни одного
  номера с двумя артикулами;
- **обратное отображение не инъективно**: 141 артикул принадлежит двум-трём
  разным KEMP-номерам (макс. 3, напр. `443959101A`). Молча сливать такие
  позиции запрещено;
- `фирма по артикулу` — 101 бренд, и он **разделяет OE от афтермаркета**:
  70.2% строк (3260) имеют бренд автопроизводителя (VAG 1591, General
  Motors 449, Mercedes 345, Ford 302, Renault 167, Opel 140,
  Peugeot/Citroen 98, Fiat/Alfa/Lancia 80, Chery 69, BMW 15, Nissan,
  Mitsubishi), остальные 29.8% — афтермаркет (Sachs 283, FAG 205,
  Nissens 91, Lesjofors 87, GKN-Spidan 81, Bosch 64, Moog 62, INA, SKF…);
- битые строки: 8 строк с пустым артикулом, 1 с пустым номером;
- `Наименование` несёт применимость открытым текстом («Амортизатор задний
  VW Golf 97- седан», «VW Passat B5 96-04») — источник словаря марок и
  моделей.

**Граница применимости этого справочника, которую нельзя переоценить.**
Номера `2141006` в файле **нет**. Справочник покрывает только KEMP-ассортимент
и не решает кейс со скриншота (крышка Metzger). Он закрывает Ф-1 для 4646
позиций, но не заменяет WP-1: для не-KEMP товаров источником идентичности
остаётся описание собственной карточки.

**Наблюдаемое следствие** (карточка 2141006, 15 кандидатов):
`COMPARABLE 0 · REVIEW 0 · SKIP 15`, из них `OEM_NOT_FOUND` 9,
`BRAND_MISMATCH` 5, `CATEGORY_NOT_AUTOPARTS` 1, при `запросов: 1`
и покрытии Prom 100%. Это не сбой сбора данных — это отсутствие
идентичности товара на входе.

## 2. ЦЕЛЕВАЯ АРХИТЕКТУРА

Порядок источников доказательства идентичности, от наиболее к наименее
доверенному. Реализуется именно в этом порядке.

```
0. СПРАВОЧНИК KEMP (kemp_reference_map)        → доверие: высшее
   4646 позиций: наш номер → реальный артикул + класс его бренда
   (автопроизводитель = OE, иначе афтермаркет). Табличный, без эвристик.
       ↓ для не-KEMP товаров и для расширения графа
1. СОБСТВЕННАЯ КАРТОЧКА (Excel-импорт)         → доверие: высшее
   Таблица аналогов + применимость из описания. Данные заказчика,
   не подлежат ценовой манипуляции третьих лиц.
       ↓ засев
2. ГРАФ КРОССОВ (CrossLink)                    → доверие: производное
   Наш номер ↔ OE производителя ↔ артикулы аналогов.
       ↓ раскрытие запросов
3. ПОИСК ПО ВСЕМ НОМЕРАМ ГРАФА                 → расширение выдачи
   Вместо 1 запроса — N запросов по номерам из графа.
       ↓ сбор
4. ОПИСАНИЯ КОНКУРЕНТОВ (существующий stage A+B) → доверие: низшее
   Уточняет и расширяет граф, но не создаёт CONFIRMED в одиночку.
```

Ключевой инвариант: **шаги 1–2 не трогают логику гейтов**.
`_gate_oem_identity` уже содержит ветку `evidence = "CROSS_TABLE"`
(`candidate_selection.py:707`) — ей просто нечего было найти.

### WP-1. Детерминированный парсер описания собственной карточки

**Новый модуль:** `backend/src/metis/pricing/own_card_identity.py`
(в `metis`, а не в `marko` — это чистая функция без БД, как остальной
`metis.pricing`).

**Контракт:**

```python
def extract_own_card_identity(
    description: str | None,
    config: OwnCardIdentityConfig,
) -> OwnCardIdentity:
    """Разобрать HTML-описание карточки в номера и применимость.

    Чистая функция: без сети, без БД, без времени, без random.
    Один вход → один выход, всегда.
    """
```

`OwnCardIdentity` (frozen dataclass, slots) содержит:

- `cross_numbers: tuple[CrossNumber, ...]` — где `CrossNumber` это
  `(manufacturer_raw, manufacturer_norm, article_raw, article_norm,
  row_index, table_caption)`;
- `applicability: tuple[ApplicabilityRow, ...]` — `(brand_raw, brand_norm,
  model_raw, generation_raw, row_index)`;
- `extraction_details: Mapping[str, Any]` — что именно распознано,
  для аудита;
- `anomalies: tuple[str, ...]` — коды проблем разбора.

**Новый конфиг:** `backend/config/own_card_identity.yaml` со
`schema_version`, `method_version`, и секциями:

- `table_captions` — заголовки распознаваемых таблиц
  («каталожні номери аналогів», «кросс-номера», «застосування»,
  «применимость» и их варианты);
- `column_headers` — («виробник»/«производитель»/«manufacturer»),
  («артикул»/«номер»/«article»), («марка / модель»);
- `article_shape` — длины и допустимые символы номера, повторно
  используя уже согласованные значения из `crosses.yaml:extraction`
  (`alphanumeric_min_length: 6`, `numeric_min_length: 7` и т.д.) —
  **не выдумывать новые пороги, а сослаться на существующие**;
- `manufacturer_aliases` — нормализация «LAND ROVER»/«Land Rover»/
  «ROVER»/«MG» в канонические ключи.

**Требования к разбору:**

- Основной путь — структурный: HTML-таблица, шапка распознана,
  ячейки читаются попарно (виробник, артикул). Таблица в описании
  Prom может содержать 3 пары колонок в одной строке — обрабатывать
  все пары, а не первую.
- Резервный путь по regex допускается **только** при отсутствии
  распознанной таблицы и обязан помечать результат
  `anomaly = "UNSTRUCTURED_FALLBACK"`, что понижает статус до REVIEW
  в WP-3.
- Самоссылка (наш собственный номер в таблице аналогов) отбрасывается
  с кодом `SELF_REFERENCE` — этого требует
  `CheckConstraint ck_cross_link_distinct_oems` (`models.py`).
- Нормализация номеров — **только через существующий**
  `normalize_cross_oem` из `metis.pricing.crosses`. Новую функцию
  нормализации не вводить: расхождение нормализаций между засевом и
  чтением в `_confirmed_cross_oems` даст молчаливый промах по графу.

**Тесты:** `backend/tests/test_own_card_identity.py` — прогон по всем
60 позициям golden-фикстуры плюс вся матрица вариаций из CONSTRAINT_5.
Метрика закрытия: **precision по номерам = 1.00** (ни одного ложного
номера — он утечёт в цену), recall ≥ 0.95, отчёт по каждому промаху.

### WP-3. Засев `CrossLink` из собственной карточки

**Архитектурное препятствие, которое надо решить сознательно.**
`CrossLink.pricing_run_id` объявлен `NOT NULL` с `ForeignKey` на
`pricing_runs.id` (`models.py`), а UniqueConstraint включает
`pricing_run_id`. Кросс из собственной карточки к прогону цен не
относится. Выбрать один из двух путей и обосновать выбор письменно:

- **(A)** сделать `pricing_run_id` nullable, добавить частичный
  UniqueConstraint для строк с `pricing_run_id IS NULL` по
  `(workspace_id, our_oem_norm, extracted_oem_norm)`;
- **(B)** отдельная таблица `catalog_identity_links` с той же формой,
  и `_confirmed_cross_oems` читает объединение двух источников.

Рекомендация: **(B)** — она не трогает существующий append-only
инвариант прогонов и не требует ослаблять NOT NULL, но требует
аккуратного UNION в чтении. Решение принимает исполнитель, но молча
менять NOT NULL на nullable без записи обоснования запрещено.

**Правила статуса:**

- структурная таблица распознана, номер нормализован, самоссылки нет,
  аномалий нет → `CONFIRMED`, `extraction_method = "OWN_CARD_TABLE"`;
- сработал `UNSTRUCTURED_FALLBACK` либо есть любая аномалия → `REVIEW`;
- никогда не `REJECTED` от этого источника: отсутствие данных ≠
  опровержение.

**`raw_context`** заполняется фрагментом исходного HTML строки таблицы —
это доказательство для аудита, оно обязано позволять человеку глазами
проверить решение.

**Чтение.** `_confirmed_cross_oems` (`catalog_discovery.py:713`)
расширяется на новый источник. Функция уже строит симметричное
замыкание по обоим направлениям пары — сохранить это свойство.
Транзитивность (A↔B, B↔C ⇒ A↔C) **не вводить** в этом WP: она
многократно увеличивает риск ложного слияния разных деталей.
Отдельный вопрос, отдельное измерение, отдельное решение.

### WP-4. Идемпотентный переразбор существующего каталога

## 5. ЧЕГО ДЕЛАТЬ НЕЛЬЗЯ

```
NO_1  Не ослаблять гейты ради роста COMPARABLE. Если после всех WP
      кандидатов по-прежнему мало — это ответ рынка, а не повод
      понижать порог. Рост метрик достигается доказательствами,
      а не смягчением проверок.

NO_2  Не вводить LLM в тракт, влияющий на цену (см. CONSTRAINT_2).

NO_3  Не вводить транзитивное замыкание графа кроссов в рамках
      этой задачи.

NO_4  Не переписывать существующие строки cross_links.

NO_5  Не подставлять артикул продавца в oe_norm — это исходный дефект,
      воспроизводить его в новом коде запрещено.

NO_6  Не сливать автоматически позиции, делящие один артикул
      (141 случай в справочнике KEMP). Только ручной разбор.

NO_7  Не смешивать доверие источников: кросс из собственной карточки и
      кросс из описания конкурента обязаны различаться по
      extraction_method и оставаться различимыми в аудите навсегда.
```

## 6. ПОРЯДОК И ЗАВИСИМОСТИ

```
WP-0 (измерение, блокирующий)
  ├→ WP-1A (справочник KEMP) ─┐
  └→ WP-1  (парсер описаний) ─┤
       └→ WP-2 (модель)       ├→ WP-4 (переразбор) → WP-5 (поиск+словарь) → WP-6 (UI)
            └→ WP-3 (засев)  ─┘
```

WP-1A делается первым: он дешевле, точнее и сразу даёт результат на 4646
позициях. WP-1 не отменяется — он нужен для не-KEMP товаров (кейс 2141006)
и для расширения графа за пределы 1:1. WP-2 не мержится раньше, чем
готов хотя бы один из двух источников OE.

Каждый WP закрывается: код + тесты + числа в отчёте
`docs/METIS_OWN_CARD_IDENTITY_EXECUTION_2026-07-28.md`, который ведётся
инкрементально по ходу работы, а не пишется в конце по памяти.
