## 5. Дефекты, найденные прогоном и hostile-перепроверкой

### 5.1. 301 на странице за концом выдачи уничтожал всю позицию

Prom сообщает `total`, превышающий то, что реально отдаёт: запрос `8E0121251L`
заявил 67, отдал 66 на трёх страницах. Условие остановки
`len(seen) >= total` не срабатывает, запрашивается страница 4, приходит
`301` на канонический URL. Клиент считал любой 3xx терминальным, `strict=True`
поднимал исключение — и **все 66 уже собранных товаров отбрасывались**.

Потеряно 2 позиции из 30 (6.7%). На 29 000 это была бы систематическая потеря.

Первая реализация исправления была слишком широкой: она принимала **любой**
`3xx` на странице >1. Это могло скрыть challenge redirect, перенос endpoint
или redirect на другой host.

Финальное правило fail-closed принимает только одновременно выполненные
условия:

1. status строго `301`;
2. page >1;
3. `Location` присутствует;
4. scheme, host и path не меняются;
5. query полностью совпадает после удаления только точного `page=N`;
6. target URL не содержит нового `page` или fragment.

`302/307/308`, смена host/path/query, отсутствие `Location` и redirect первой
страницы остаются ошибками. Допустимый `301` сохраняется как raw capture с
SHA-256 и входит в request/status telemetry. Уже собранные товары сохраняются.

### 5.2. Любая ошибка сбора оставляла прогон в статусе `running`

`session.rollback()` в обработчике ошибок обесценивает атрибуты ORM-объекта.
Следующая строка читала `run.id` как аргумент `session.get(...)` — это
триггерило ленивую загрузку вне async-контекста и падало с `MissingGreenlet`.
Итог: настоящая причина терялась, а строка навсегда оставалась `running`
без `error_code`.

Исправлено: идентификатор читается до `try`. Проверено на живой БД —
статус `failed`, код и текст ошибки записываются.

Обе позиции пересобраны после исправления: `#5 8E0121251L` → 66/67,
`#7 314216` → 160/162.

### 5.3. Отчёт скрывал два реально выполненных `301`

Gateway правильно останавливал пагинацию, но `_collect_live()` возвращал
только успешные `200` traces. Поэтому база и отчёт показывали 107/107 `200`,
хотя upstream получил 109 запросов.

Исправлено: orchestration возвращает и сохраняет все traces. Допустимый
pagination-stop проходит отдельную строгую проверку, получает evidence blob,
status `301`, attempts и latency. Полный повторный batch подтвердил:
`200` ×107 + `301` ×2 = 109.

### 5.4. Пустой рынок мог ошибочно выглядеть как CAPTCHA

Проверка «нет товаров + в HTML встречается recaptcha» недостаточна: маркеры
чата присутствуют и на валидной пустой выдаче. Теперь сначала фиксируется
parser outcome. `EMPTY_SEARCH_RESULT` не является блокировкой; неразбираемое
тело с blocking-маркерами — подозрение на блокировку; parser schema error без
маркеров остаётся отдельной диагностикой, а не «нулевым рынком».

### 5.5. Resume и automation не были полностью fail-closed

Checkpoint identity содержал хэш файла целей, но `pending()` не проверял, что
записанный `sample_no` всё ещё соответствует тому же `oe_norm`, и не отклонял
лишние sample numbers. Обе проверки добавлены.

`report` раньше возвращал exit code 0 даже при `failed/not_attempted` строках.
Теперь полный отчёт возвращает 0, неполный — 1. Проверено живым сценарием:
после первых 5 целей report вернул 1; после resume до 30/30 — 0.

## 6. Что построено (1.2)

`catalog-coverage-measurement` — CLI с двумя подкомандами:

- `collect` — живой сбор, одна позиция = одна транзакция = одна строка
  чекпоинта (JSONL, `fsync` после каждой). Прерывание стоит максимум одной
  позиции в работе.
- `report` — сети не касается, пересчитывает все метрики из сохранённых
  доказательств; отчёт можно перевыпустить без повторного парсинга.

Возобновление fail-closed: чекпоинт продолжается только батчем с тем же
хэшем списка целей и теми же влияющими на результат настройками
(лимит страниц, sha256 конфига отбора, датасет брендов, задержки, попытки).
Иначе — отказ с перечислением расхождений, чтобы в один файл не попали
наблюдения из двух разных конфигураций.

Резюмируемость перепроверена не только тестами: новый append-only batch шёл
двумя независимыми командами (5 целей → resume оставшихся 25). Первые пять
запросов не выполнялись повторно; checkpoint содержит ровно один header и 30
уникальных completed records.

## 8. Открытые вопросы (решение — за пределами Гейта 1)

1. **`norm_oem` не срезает ведущие нули**, хотя §2.1 плана это предписывает:
   `strip_leading_zeros(remove([^A-Z0-9], upper(s)))`. Реализация делает только
   `remove([^A-Z0-9], upper(s))`. Затрагивает цель `026129589A` и любую с
   ведущим нулём. Изменение сдвинет идентичность по всему конвейеру, поэтому
   выносится решением, а не побочным эффектом замера.
2. **Одной позиции не хватило 10 страниц**: `#30 1F0129620` — 290 из 393,
   `SEARCH_PAGE_HARD_CAP`. Потолок надо поднимать или принимать осознанно.
3. **Prom завышает `total`** (67 против 66, 162 против 160). Разрыв явно
   помечен `UPSTREAM_RESULT_GAP`: уже собранные данные не отбрасываются, но
   недоступные upstream-позиции не объявляются полученными.
4. **Наличие**: 624 из 2633 предложений помечены «нет в наличии», значений
   «неизвестно» — 0. Для когорты C это существенный фильтр.
