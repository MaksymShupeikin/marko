## 2. Поиск по номеру производителя (главное архитектурное изменение)

Поиск конкурентов идёт по **каталожному номеру**, а не по внутреннему
артикулу магазина. Три пути добычи номеров:
- колонка `Пошукові_запити` XLSX-экспорта (`parsers/prom_export.py`);
- атрибуты Apollo страницы товара — «Код запчастини», «Кросс-номери»
  (`services/parser_models.py`, `_numbers_from_attributes`);
- одноразовая дозагрузка страницы, когда номеров нет в базе; результат
  пишется в `raw_data` (`set_listing_oem_numbers`).

Общий разбор — `parsers/part_numbers.py`; `order_numbers` ставит номер
с буквой первым (в поиск идут только первые 2–3 терма, чисто цифровой
токен — внутренний артикул, по нему конкурентов не найти).

Марка KEMP (86% каталога) вычищается из запросов к сайтам
(`_market_brand`), но **остаётся для avto.pro** — он ищет по марке,
без неё выдача пустая.

## 3. Конвейер отчёта и его гейты (в порядке выполнения)

1. **4 источника параллельно**: Avtopro, Prom, Exist, Google (Serper).
   Лимиты: `_AVTOPRO_MAX_OFFERS=40` (3 номера), `_PROM_MAX_OFFERS=60`,
   `_GOOGLE_MAX_OFFERS=20`, страниц докачки `_SERP_MAX_PAGE_FETCHES=12`.
2. **Первый проход модели** per-source (`llm_filter.classify`):
   same / analog / no. Аналог на ту же машину идёт в статистику с
   доверием 0.75 (`_ANALOG_CONFIDENCE`) — для własной марки без аналогов
   рынка не существует в принципе.
3. **Жёсткие отсевы** (`offer_gates.py`, детерминированные): словарь
   Б/У на двух языках, «ціна за запитом», плюс машинные флаги avto.pro
   `data-bu="1"` / `data-is-cardismantling`.
4. **Валюты и правдоподобие**: НБУ-конвертация, `_drop_implausible`
   (нули, склейки), отсев выбросов ×8 от медианы.
5. **Текстовая перепроверка** (`_verify_offers` → `llm_filter.verify_offers`):
   модель видит цену/продавца/наличие/состояние + медиану. `ok` — живёт,
   `drop` — вылет, `unsure` — понижение до 0.5 **только** если цена <
   медиана/2.5. Требует ≥3 уверенных цен (`_VERIFY_MIN_CONFIDENT`).
6. **Фото-проверка** (`_photo_check_offers`, НОВОЕ, `983f9be`) — см. §4.
7. Статистика: `_stats_prices` (confidence ≥ 0.7; если сильных меньше
   `_MIN_STATS_SAMPLE=3`, а всего хватает — считаем по всем),
   рекомендация = min × 0.94.

## 4. Фото-проверка Б/У (коммит `983f9be`, 30.08)

**Зачем**: насос с разборки за 1400 ₴ без слова «б/у» в тексте задавал
рекомендацию 1316 ₴ при рынке новых от 2500. Текст чистый, флагов у Prom
нет — единственная улика была на фото (маркер «А6С7», затёртый корпус).

**Как устроено**:
- `services/photo_check.py` — кеш вердиктов в Redis по URL объявления:
  `photo-used:v1:{sha1(url)}`, TTL 7 дней («unsure» — сутки); мёртвый
  Redis деградирует до прямых вызовов;
- `llm_filter.photo_condition` — vision-вызов (`_ask_openai` обобщён:
  `image_url=` шлёт контент частями, `model=` переопределяет модель);
  промпт `_PHOTO_SYSTEM` требует **сначала улику, потом вердикт** и явно
  запрещает считать фон доказательством (в Украине новые детали снимают
  на картоне — живая проверка ловила новый радиатор KEMP как «used»,
  пока это не запретили);
- `_photo_check_offers` в `competitor_prices.py`: смотрит только
  `_PHOTO_CHECK_CHEAPEST=3` самых дешёвых из статистики (без известного
  состояния) + всё подозрительно ниже медианы (там «нове» тоже
  проверяется), потолок `_PHOTO_CHECK_MAX=4` фото на отчёт;
- применение вердикта **ступенчатое**: `used` + подозрительно дёшево →
  полный отсев; `used` при рыночной цене → видим, помечен «used», но
  confidence 0.5 (вне статистики) — защита от дрожащего вердикта на
  граничных фото; `unsure` понижает только подозрительно дешёвые;
  **сбой vision-вызова ≠ вердикт** — предложение нетронуто (иначе
  провайдер без зрения давил бы честные цены);
- флаги: `COMPETITOR_PHOTO_CHECK_ENABLED` (по умолчанию true),
  `COMPETITOR_PHOTO_MODEL` (пусто = модель фильтра);
- Google/Exist достают фото из JSON-LD (`_structured_price` теперь
  возвращает тройку `(price, currency, image)`; `_ld_image`).

**Живой результат**: отчёт по 06E145100R — рекомендация поднялась с
1316 до **2566 ₴**, насос за 1400 исчез, VLAN за 2500 помечен «used»
и вне статистики.

**Правило версий**: меняешь семантику `_PHOTO_SYSTEM` — поднимай
`photo-used:v1`, иначе неделю применяются вердикты старого промпта.

## 5. Рассрочка из сниппета — не цена (коммит `b9c301e`, 30.08)

Rozetka отдаёт ботам 403 → страница не открылась → цена пришла из
сниппета Google, а там только «від 365 ₴ x 6 ; від 365 ₴» (рассрочка,
2190/6). Отчёт показал амортизатор за 2190 как «365».

Фикс: `_INSTALLMENT_PRICE_RE` ловит платежи («N ₴ x 6», «N грн/міс»),
и `_price_from_text` не считает такое число ценой **ни в одном
вхождении** текста (платёж повторяется и без маркера). Итог для таких
сниппетов — предложения нет вовсе: честнее, чем месячный платёж вместо
цены. Тест: `test_installment_payment_is_not_a_price`.

```
_SUSPICIOUS_LOW_FACTOR = 2.5           _VERIFY_MIN_CONFIDENT = 3

```

- Кеш отчётов: `competitor-prices:v11:{listing_id}:{sha1}` —
  **меняешь форму/семантику отчёта → поднимай версию**.
- Кеш фото-вердиктов: `photo-used:v1:{sha1(url)}` — то же правило.
- **Голова миграций: `20260829_0013`** (ремонт разошедшейся 0012 —
  коллизия случилась из-за параллельной работы двух веток; новые ревизии
  → `down_revision = "20260829_0013"`).
- `backend-test` без volume mount → `--build` обязателен:
  `docker compose -p marko run --rm --build backend-test`.
- Общее имя Docker-проекта `marko` затирает сборки при параллельной
  работе двух копий репозитория.
- Инварианты не регрессировать: `unsure` (текст и фото) понижает только
  подозрительно дешёвые; Б/У avto.pro ловится флагом `data-bu`, не
  текстом; `_stats_prices` не схлопывает выборку до одной цены;
  группировка ранжирует до фильтров; `list_stores` отдаёт полный кортеж.

## 7. Открытые вопросы (без слова заказчика не начинать)

1. **Exist.ua молчит**: `ExistPriceSource` написан, но бесплатный Serper
   запрещает `site:` — источник отдаёт `skipped` через `_SourceUnavailable`.
   Нужен платный Serper или обход Cloudflare.
2. **Кросс-номера Exist** («Оригінальні номери»: Kemp 776… → VAG …):
   сперва померить разрыв по базе (сколько позиций только с кодом 776…),
   потом решать про догрузку по требованию.
3. **Разброс первого прохода**: тот же товар — то 3, то 29 предложений,
   рекомендация гуляла 485↔1366. Блокер для будущего «пробега по 500
   товарам». Намеренно не начат.
4. **avtofishka (стенд второго пользователя), диагноз готов, фиксов нет**:
   (а) на Prom два магазина со слагом avtofishka — `c2875920` и
   `c3532981`; товар в обоих даёт две одинаковые подписи в «Ваші
   магазини» — нужно различать одноимённые магазины (номер компании/URL);
   (б) артикулы у продавца повторяются **внутри** магазина (SKU `0005` —
   два разных товара) — группировка склеивает разные товары; фикс:
   не группировать листинги с одним SKU внутри одного магазина.
   Парсинг Prom при этом **цел** — проверено живым прогоном обоих
   магазинов; «Failed to fetch /jobs/active» на чужом стенде — их API
   лежал, нужен их лог и коммит.
5. **«від N ₴»** (цена «от») из сниппета всё ещё берётся как цена;
   товары «немає в наявності» не отсеиваются — осознанно, но можно
   пересмотреть.
6. **Flutter Web**: текст не копируется (canvas-рендер) — план: 
   `SelectionArea` на панель товара + кнопки копирования артикула/OEM;
   3.2 c до первого кадра — план: сплэш в `index.html`, проверить
   brotli/кеш на `main.dart.js`.
7. **Мердж `marko-core` → `main` и деплой** — прод живёт кодом до всех
   фиксов.
8. Идея заказчика (обсуждена, одобрена мной с оговорками): **пробег по
   N товаров одной кнопкой** → Excel с листами «Поднять / Опустить /
   Рынка нет» (+ совместимость с обратным импортом цен Prom). Требует
   сперва закрыть п.3 (детерминизм) — иначе кривые отчёты молча лягут
   в файл.
