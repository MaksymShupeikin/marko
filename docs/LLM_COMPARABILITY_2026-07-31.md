# LLM-проверка сопоставимости товаров

Дата: 2026-07-31
Статус реализации: код и миграция готовы; внешний провайдер по умолчанию выключен.

## Назначение

Этап проверяет, можно ли использовать конкретное предложение конкурента как
ценовой ориентир для нашего товара. Он находится между сохранением результата
Prom-парсера и расчётом рекомендации.

```text
Prom parser
  -> immutable MarketObservation + candidate_snapshot
  -> deterministic hard stops
  -> cached multimodal LLM review
  -> only COMPARABLE + EXACT/ACCEPTABLE_ANALOGUE
  -> pricing engine
  -> recommendation UI
  -> manual customer decision
```

Marko не публикует и не меняет цены на Prom.ua. API провайдера получает только
данные для проверки пары товаров и возвращает классификацию; у него нет
инструмента или credentials для изменения карточек.

## Контракт решения

Каждая проверка сохраняет:

- `COMPARABLE`, `NOT_COMPARABLE` или `INSUFFICIENT_DATA`;
- `EXACT`, `ACCEPTABLE_ANALOGUE`, `SUSPICIOUS` или `NOT_APPLICABLE`;
- уверенность от 0 до 1;
- краткое обоснование;
- выводы по отдельным признакам и ссылки на конкретные поля;
- жёсткие противоречия;
- входной снимок, использованные изображения, модель, prompt/schema version,
  response ID, latency, token usage и безопасный код ошибки.

Положительный вердикт обязан содержать подтверждённый `part_type` и не может
содержать жёсткого противоречия.

## Жёсткие стоп-признаки

Детерминированный конфликт в любом из полей ниже исключает кандидата до вызова
LLM и не может быть отменён LLM или пользовательской коррекцией:

- OE/cross identity;
- тип детали;
- применимость, поколение, годы, двигатель и кузов;
- сторона и позиция установки;
- состояние;
- количество/комплектация.

Бренд и его ценовой уровень сами по себе не являются конфликтом. Это реализует
решение заказчика сравнивать бюджетный сегмент с самым дешёвым действительно
сопоставимым аналогом.

## Режимы

`PRICING_LLM_COMPARABILITY_MODE`:

- `off` — безопасное значение по умолчанию; старый детерминированный контур;
- `shadow` — проверки сохраняются и показываются, но пока не меняют выборку;
- `required` — в расчёт попадают только положительно проверенные кандидаты.

В `shadow` и `required` обязательны `PRICING_LLM_API_KEY` и
`PRICING_LLM_MODEL`. Финализатор run имеет отдельный барьер и не начинает
калибровку, пока для каждого кандидата в `classified`-позиции не сохранён
результат проверки либо fail-closed результат ошибки. Кандидаты уже
терминально `failed`/`cancelled` позиции не блокируют весь run и всё равно не
попадают в её ценовую рекомендацию.

Рекомендуемый порядок включения:

1. Установить secret и включить `shadow`.
2. Собрать независимые подтверждения/исправления заказчика.
3. Измерить precision положительного класса отдельно для `EXACT` и
   `ACCEPTABLE_ANALOGUE`.
4. Разобрать все ложноположительные и hard-stop расхождения.
5. Только после согласованного порога качества включить `required`.

## Провайдер и формат

Реализован `openai_responses` через Responses API:

- строгий Structured Output (`text.format.type=json_schema`);
- текстовые поля и до четырёх безопасных HTTPS-изображений;
- `store=false`;
- короткий retry только для transport/429/5xx;
- отказ, timeout, некорректная схема или неожиданный ответ сохраняются как
  `INSUFFICIENT_DATA` и никогда не допускают кандидата к расчёту.

Marketplace-текст считается недоверенным. System instructions запрещают
исполнять команды из названия, описания, характеристик, URL или изображения.

## Кэш

Ключ кэша включает:

- версию входной схемы и prompt;
- модель;
- данные нашего товара;
- содержимое карточки кандидата, цену и изображения.

Run-specific `observation_id` исключён из content hash, поэтому повтор того же
содержимого карточки не вызывает новый платный запрос. Изменение содержимого
создаёт новый ключ. Ручной `force=true` обходит кэш.

Если заказчик уже исправил или подтвердил совпадающую проверку, её человеческая
разметка имеет приоритет над более свежей некорректированной машинной
cache-копией.

## Обратная связь

Заказчик может подтвердить вывод либо создать append-only коррекцию. Новая
запись не переписывает исходный LLM-ответ и формирует собственный набор
размеченных соответствий. Положительная коррекция не может обойти
детерминированный hard stop.

API:

- `GET /api/v1/pricing/comparability/status`;
- `POST /api/v1/pricing/observations/{id}/comparability-reviews`;
- `POST /api/v1/pricing/comparability-reviews/{id}/feedback`;
- evidence рекомендации содержит `candidate_snapshot`, `llm_review_required`,
  `llm_pricing_eligible` и полный `llm_review`.

Все изменяющие endpoints требуют роли администратора workspace.
Интерфейс показывает значения нашего товара и кандидата, поля/фрагменты
доказательств, hard stops, использованные фото, источник решения и кэш.

## Аудит и воспроизводимость

Review и feedback таблицы append-only. Эффективный человеческий вердикт и
конкретные review snapshots входят в calculation trace, decision fingerprint
v3 и replay contract v6. Поэтому последующая разметка не меняет задним числом
старую рекомендацию: она применяется только к следующему расчёту.

## Что требуется для реального запуска

Локальные mock-тесты не доказывают точность на товарах заказчика. До
`required` нужны:

- реальный API key в secret store;
- ограниченный shadow-run;
- вручную размеченная репрезентативная выборка;
- отдельно зафиксированные false-positive/false-negative;
- подтверждённый заказчиком порог качества.
