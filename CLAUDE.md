# Правила работы над Marko

## Что читать перед задачей

1. `docs/product-vision.md` — суть продукта и главный сценарий.
2. `docs/ui-behavior.md` — что должна делать каждая кнопка и какие у неё
   состояния.
3. `docs/parser-spec.md` — контракты парсеров prom.ua / XLSX / avto.pro.
4. `docs/known-gaps.md` — список известных расхождений «должно / есть».

Эти файлы — источник истины о поведении. Код с ними расходится → это баг в
коде. Спека кажется неверной → сначала предложи правку спеки, потом меняй код.

## Главное правило

**Зелёные тесты не значат, что фича работает.**

Проверка через API с полным набором параметров и проверка через интерфейс —
разные вещи. Живой пользователь проходит по UI, где параметры теряются
(живой пример — G2 в `known-gaps.md`: бэкенд умеет отсекать чужую марку по
названию товара, но клиент название не отправляет; в тестах всё зелёное, у
человека — мусор в выдаче).

Поэтому фича считается сделанной, только когда пройден путь пользователя:
открыл экран → нажал кнопку → увидел результат. Если такой проверки не было,
так и напиши в отчёте — не выдавай непроверенное за работающее.

## Чеклист для любого элемента интерфейса

Прежде чем считать кнопку готовой, проверь все состояния:

- [ ] **loading** — кнопка заблокирована, спиннер внутри неё;
- [ ] **success** — виден результат, а не просто исчезнувший спиннер;
- [ ] **empty** — текст, объясняющий пустоту, и следующее действие;
- [ ] **error** — текст на языке пользователя (не `Exception`, не HTTP-код) и
      способ повторить;
- [ ] данные, которые можно подставить автоматически (OEM, бренд, магазин),
      подставлены — пользователь не вводит их руками;
- [ ] долгая операция переживает закрытие модала.

## Чеклист для парсеров

- [ ] изменение верстки источника даёт `ParseError` с понятным текстом, а не
      пустой список (пустой список читается как «конкурентов нет» — это ложь);
- [ ] сеть отделена от разбора HTML;
- [ ] ретраи только на 429/5xx, паузы между запросами сохранены;
- [ ] проверено на живом запросе, а не только на фикстуре;
- [ ] эталонные номера из `parser-spec.md` §3 дают ожидаемую марку.

## Порядок работы

1. Найди пункт в `known-gaps.md` или заведи новый.
2. Уточни ожидаемое поведение в спеке; неясное — спроси у владельца, не
   додумывай (в спеках такие места помечены `> ❓ Решить`).
3. Сделай минимальное изменение.
4. Прогони тесты: `make test` (backend) и `flutter test` (frontend).
5. Проверь руками через интерфейс на реальных данных.
6. Обнови `known-gaps.md` и спеку, если поведение изменилось.

## Технические заметки

- Backend: FastAPI + SQLAlchemy + Celery, `backend/src/marko/`.
- Frontend: Flutter + Riverpod, `frontend/lib/`; HTTP только в `*_api.dart`,
  состояние — в контроллерах, виджеты в сеть не ходят.
- Firebase используется **только** для аутентификации; бизнес-данные — в
  PostgreSQL через FastAPI.
- Язык интерфейса — украинский; язык документации — русский.
